NATIVE LOCKSTEP GATE: N CLIENTS AND INPUT WIRE 3 - 29 OCTOBER 2026

SCOPE
Opt-in extension of the native FrameTick gate (src/native/engine/lockstep_gate.c,
tools/dev/native_gate_relay.py, tools/dev/native_gate_probe.lua) from two to
N = 2..8 full-simulation clients behind one loopback coordinator relay, with one
opaque variable-length input blob per client and tick. Protocols 1 and 2 are
unchanged and remain the default: without the configuration below every
packet, digest and report is the same as before. Evidence at this revision is
offline (C and Python unit tests); no native N-client game has been run.
Protocol 4 (PROTOCOL 4: LOOKAHEAD WINDOW below) carries the same input wire
with a bounded permit window, for relays one internet round trip away.
Protocol 5 (PROTOCOL 5: ADAPTIVE WINDOW below) lets the relay choose that
window from measured round trips and change it during a session.
WIRE CRYPTO below seals and signs protocols 3 and 4 (opt-in, 1 November 2026).

PROTOCOL 3 MESSAGES
ASCII, fields separated by '|', UDP on 127.0.0.1.

Client to relay, resent every 100 ms until answered:
  NGSTATE|3|<token>|<slot>|<tick>|<game>|<real>|<digest>|<clients>|<blob>
    token    32 lowercase hex (session token)
    slot     1..N, canonical decimal (no sign, no leading zero)
    tick     0..--ticks, canonical decimal; the frame just completed
    game     16 lowercase hex: bits of the IEEE-754 double game time
    real     16 lowercase hex: bits of the double real time
    digest   64 lowercase hex: the client's declared state digest for tick
    clients  N as configured on the client; refused unless equal to --clients
    blob     0..480 lowercase hex characters, even length (0..240 bytes);
             may be empty. This client's sealed proposal for tick.
  The datagram is at most 1024 bytes (the largest valid one is 647).

Relay to every client once all N reported tick:
  NGGO|3|<token>|<slot>|<tick+1>|<blob 1>|<blob 2>|...|<blob N>
    exactly N blob fields in slot order (empty fields allowed): the sealed
    proposals all clients reported for tick. At most 3,910 bytes for N=8;
    the native receive buffer is 8,192 bytes.
  NGSTOP|3|<token>|<slot>|<tick>
    end at --ticks or failure, as in protocols 1 and 2.

Protocols 1 and 2 (unchanged, two players for protocol 2):
  NGSTATE|1|<token>|<slot>|<tick>|<game>|<real>|<digest>
  NGSTATE|2|<token>|<slot>|<tick>|<game>|<real>|<digest>|<command: 8 hex>
  NGGO|1|<token>|<slot>|<tick+1>
  NGGO|2|<token>|<slot>|<tick+1>|<command 1>|<command 2>
  NGSTATE datagrams of protocols 1 and 2 stay limited to 512 bytes.

DETERMINISM CONTRACT
- A client's blob for tick t is sealed by its report for t. It is sent with
  NGSTATE t and returned to every client, in slot order, in NGGO t+1. Lua sees
  those blobs in s.inputs when s.issued == t+1, so the blobs applied at a tick
  are byte-identical on every client and come only from the relay's permit.
- Proposals of the final tick are never applied (the relay answers NGSTOP).
- The relay releases tick t only when all N clients reported t with the same
  game time, the same real time (or, with --relative-real, the same elapsed
  real time t/hz since tick 0) and a 1/hz game step (--tick-hz, the clients'
  native_gate_tick_hz, default 60). A changed retransmission
  of any field, including the blob, fails: changed_state_while_waiting_tick_t.
- Digest mismatches fail the session (battle_state_mismatch_tick_t) or, with
  --observe, are recorded per tick with the slots that differ from slot 1.
- The relay locks to the first admitted protocol. Protocol 2 needs
  --clients 2; protocols 1 (no inputs) and 3 admit any N in 2..8.
- The relay silently drops: wrong token, non-loopback sender, unknown slot,
  non-canonical slot/tick, clients field different from --clients, blob with
  uppercase/other characters, odd length or more than 480 characters, wrong
  field count, datagrams above the size limit, and other protocol versions.
- The gate stops with reason 56 when a permit returns a different blob for
  its own slot, ignores malformed permits (the 60 s wait then ends with
  reason 7) and stops with reason 8 on a datagram of 8,192 bytes or more.

NATIVE LUA INTERFACE (x4lan_gate_64.dll; stable for input adapters)
gate.wire(version, clients) -> 1 or 0
  Call before gate.start/gate.boot. (2, 2) is the default; (3, N) with
  N = 2..8 selects protocol 3 and needs lua_rawseti from X4's Lua runtime.
  Once started, only the identical configuration returns 1 (UI reloads).
  Slots 1..N are then admitted by gate.start/gate.boot.
gate.propose(tick, blob) -> 1 or 0
  Protocol 3 only; tick must equal s.issued; blob as on the wire. Before the
  report of that tick it stages (and may replace) the proposal; after the
  report it returns 1 only for the sealed blob.
gate.report(tick, hash, blob) -> 1 or 0
  Protocol 3: blob nil seals the blob staged for this tick, or the empty
  blob; an explicit blob must be valid and agree with a staged one. A repeated
  report of the same tick must carry the same blob. Protocol 2 is unchanged
  (third argument: 8-hex command).
gate.lookahead(k) -> 1 or 0
  Protocol 4 window k = 1..8 (0 keeps protocol 3); after gate.wire(3, N),
  before gate.start/gate.boot; once started only the identical k returns 1.
gate.lookahead_status() -> "lookahead=k ready= ahead_max= idle= resends=
  stale= duplicates=" (ready: frames whose permit had arrived before it was
  needed; ahead_max: farthest permit received ahead of the completed tick;
  idle: 25 ms receive timeouts while waiting).
gate.poll() -> s
  s.wire_version  2 or 3 (3 also for protocol 4)
  s.clients       N
  s.inputs        array [1..N]: admitted inputs of tick s.issued; protocol 3
                  blobs, protocol 2 the two 8-hex commands
  s.input1/input2 protocol 2 only, unchanged
  s.lookahead     protocol 4 only: k
  s.inputs_tick   protocol 4 only: the tick whose proposals s.inputs are
                  (s.issued-1-k); absent while s.issued <= k

PROBE CONFIGURATION AND INPUT ADAPTER (tools/dev/native_gate_probe.lua)
X4LAN_CONFIG.slot = "pK"                 K = 1..N (lane token @X4LANE_SLOT@)
X4LAN_CONFIG.native_gate_clients = N     enables protocol 3 (lane token
                                         @X4LANE_CLIENTS@); absent: protocol 2,
                                         slots p1/p2 only, as before
The probe calls gate.wire(3, N) before boot and logs
"NATIVE_GATE ARMED slot=pK hash_scope=... wire=3 clients=N".
Optional global adapter X4LAN_NATIVE_INPUTS:
  apply(tick, inputs, clients, slot) -> string or nil
    Once per admitted tick, before the declared state digest. inputs[1..N]
    are the admitted blobs (identical on every client). A returned string is
    appended to the digest data. Without an adapter every blob must be empty.
  proposal(tick) -> blob or nil
    After the digest; a blob is staged with gate.propose(s.issued, blob) and
    sealed by the report. nil leaves the empty blob, or whatever was staged
    through gate.propose for this tick.
The probe logs "NATIVE_GATE INPUTS tick=T blobs=b1,...,bN" when any admitted
blob is non-empty.
X4LAN_CONFIG.native_gate_lookahead = k   protocol 4 (needs native_gate_clients;
                                         k = 0 or absent: protocol 3). The probe
calls gate.lookahead(k) after gate.wire(3, N), appends " lookahead=k" to the
ARMED line, adds "proposed=<s.inputs_tick>" to INPUTS lines, checks
s.lookahead/s.inputs_tick every tick and logs "NATIVE_GATE LOOKAHEAD_STOP
<gate.lookahead_status()>" at the end.

PROTOCOL 4: LOOKAHEAD WINDOW (29 OCTOBER 2026, OPT-IN)
Why: with protocol 3 every client sends its report of tick t and waits for
the permit of t+1, which needs every client's report of t. A relay one round
trip r away therefore costs r on every frame (vps-V2: 31 ms frames became
42 ms, wait 11.2 ms = the round trip). Protocol 4 releases permits up to k
ticks ahead (window k = 1..8, relay --lookahead k, probe native_gate_lookahead
= k), so a frame waits only when the round trip exceeds k frames.

Rule. The permit for tick T needs every client's report of tick T-1-k (and
for T <= k+1 every client's report of tick 0, so the session still starts in
step) and carries exactly the proposals sealed with tick T-1-k (all blobs
empty for T <= k: there are no proposals before tick 0). A blob proposed with
tick t is therefore applied at t+1+k on every client; protocol 3 is k = 0.
The relay checks each tick (game step, clocks, digest) exactly as before and
in tick order, only up to k ticks after the clients ran it; the hold tick
delays the permit its reports release. A client never runs a tick whose
inputs it has not received: every input it applies at T is in the permit
for T, and a permit is released only after all reports it carries passed
their checks. Nothing is predicted, guessed or rolled back.

Messages (ASCII, '|', UDP; fields as in protocol 3):
  NGSTATE|4|<token>|<slot>|<tick>|<game>|<real>|<digest>|<clients>|<k>|<blob>
    k canonical decimal 1..8, equal to the relay's --lookahead; at most 649
    bytes. Sent once when the tick is sealed; while waiting for a permit the
    client resends each report of its window (ticks completed-k..completed)
    at most once per 100 ms.
  NGGO|4|<token>|<slot>|<T>|<k>|<blob 1>|...|<blob N>
    the blobs sealed with tick T-1-k in slot order; at most 3,912 bytes. The
    relay sends it to every client when released (tick 0 releases T = 1..k+1,
    tick t > 0 releases T = t+1+k, never beyond --ticks) and to one client
    again when that client resends a report of an already checked tick.
  NGSTOP|4|<token>|<slot>|<tick>
    for any tick that client reported (it may lag the newest by up to k).
The relay accepts reports up to its highest released permit and drops later
ones; out-of-order reports inside that range are kept and checked in order.

Compatibility (explicit, fail closed). A relay serves either protocols 1-3
(no --lookahead, behaviour and reports unchanged) or protocol 4 with exactly
one k, never both. An authenticated, well-formed report of the other kind or
another k fails the session (lookahead_mismatch_slot_S) and is answered with
NGSTOP in the sender's protocol; malformed or unauthenticated reports are
dropped as before. An older relay drops protocol 4 like any unknown version
(the client then stops with reason 7 after its wait timeout); an older gate
DLL has no gate.lookahead and the probe refuses (REFUSED lookahead=k).

Client (lockstep_lookahead.h). It holds the sealed reports of ticks
completed-k..completed and the permits received for completed+1..
completed+1+k, reading queued datagrams without blocking every frame (a relay
NGSTOP is seen at the next frame even while permits are held). It fails
closed: a permit beyond that window or with non-empty blobs before tick 0
stops with reason 102, a second permit for one tick with different blobs with
103, a permit that returns a different local proposal with 56 (as in
protocol 3); a stale permit (tick already run) is ignored.
Malformed datagrams, the 60 s wait (7), oversize datagrams (8), game-time
drift (5) and window close (6) behave as in protocol 3. Stop reasons 102 and
103 are new (90-98, 100, 101 and 110 are taken).

Input delays. The input wire now adds k ticks between proposal and arrival,
so adapters whose blobs name an apply tick need delay >= k+1 for player
orders (applied in the admitting tick) and >= k+2 for pilot records (staged
one tick before they apply; the native pilot_arm refuses less). The probe
checks both before loading; with the default delays of 3, k = 1 for pilot
records and k = 2 for orders are the largest windows. The native hit claims
(native_gate_hit_claims = true/'shooter'/'victim'/'first') reconstruct a
claim's observe tick relative to the sealing tick r-1-k and widen their
validation bound by k (reports/LOCKSTEP-HIT-CLAIMS-NATIVE-20261029.txt); the
Lua test carrier ('carry') still assumes k = 0.

Expected frame time. With frame cost f and round trip r between a client and
the relay (relay processing negligible), the steady state satisfies
(k+1)*P = max(k*P, r) + f, i.e. P = max(f, (r+f)/(k+1)): k = 0 gives f+r (the
vps-V2 42 ms from 31 + 11), and the round trip disappears once k*f >= r.
The slowest client and the largest round trip set P for everyone. Discrete-
event model of the native client with the real relay code (SimulatedSession
in tests/test_native_gate_lookahead.py, which asserts these values):
  r=11 ms f=31 ms: k=0 42.0, k=1..4 31.0 ms
  r=60 ms f=31 ms: k=0 91.0, k=1 45.5, k>=2 31.0 ms
  r=100 ms f=31 ms: k=0 131.0, k=1 65.5, k=2 43.7, k=3 32.75, k=4 31.0 ms
  one-way 5.5..25.5 ms uniform jitter, f=31 ms: k=0 65.6, k=1 34.6, k=2 31.0
A digest mismatch is reported at most k ticks late, and a stopped session
ends with clients up to k ticks past the failing tick.

PROTOCOL 5: ADAPTIVE WINDOW (1 NOVEMBER 2026, OPT-IN)
Why: protocol 4 fixes k and the input delays per session config, so a session
far from its relay is slow (k too small) and one next to it pays input delay it
does not need (k too large). Protocol 5 lets the relay measure every client's
round trip at tick 0 and choose k, the pilot delay with it, and (opt-in) change
k during the session. Relay: native_gate_relay.py --adaptive --lookahead KMAX
(tools/dev/native_gate_adaptive.py); client: native_gate_lookahead =
'adaptive', native_gate_lookahead_max = KMAX (default 4); native:
lockstep_adaptive.h. Report: reports/LOCKSTEP-ADAPTIVE-DELAY-20261101.txt.

Schedule. Entries (start, lag, pilot): a proposal sealed with tick c applies at
c + lag(c), where lag(c) is the lag of the last entry with start <= c; k = lag-1.
Entry 1, the plan, has start 0. pilot is the plan's pilot delay in every entry
(lag <= pilot-1). A larger lag from start c on leaves the permits between
c-1+lag(c-1) and c+lag(c) without inputs (gap permits). A smaller lag by d makes
the ticks c-d..c-1 quiet: every client seals the empty proposal there (the
probe does not ask its adapters; their inputs wait) and no permit carries them.
So the apply tick rises by exactly one per non-quiet tick except at gaps:
nothing is lost, applied twice or before it was sealed. An entry's start must
lie after the previous entry's start plus its quiet ticks; at most 32 entries.
The relay announces an entry only when every tick it changes (its start, or its
first quiet tick) is above the highest permit issued, so no client has sealed
one, and only after every client acknowledged the previous entry.

Release. Report t (not quiet) releases every permit up to c'+lag(c')-1, where
c' is the next non-quiet tick after t; quiet reports release none. Tick 0
releases permits 1..lag (1..lag-1 are gaps). The relay holds tick 0 until it has
--adaptive-samples round trips per client (default 8; pings every 20 ms), or
--adaptive-measure-seconds (5) passed and a client has fewer than 2: stop
adaptive_unmeasured_slot_S. Choice: r = slowest client's p90 round trip, f =
1000/tick_hz ms, target period 1000/--adaptive-target-hz (default tick_hz):
k = clamp(ceil((r + margin + f)/target - 1), --adaptive-min, --lookahead),
margin --adaptive-margin-ms (10); pilot delay k+2+--adaptive-headroom (0).
Session changes (--adaptive-changes; lowering also --adaptive-decrease): every
--adaptive-interval s (2), from the pings of the last interval (every 200 ms):
raise to the k the low end of the round-trip ranges needs, lower to the one
their high end allows after 3 intervals in a row; never above pilot-2.

Messages (ASCII, '|', UDP; fields as in protocol 4):
  NGSTATE|5|<token>|<slot>|<tick>|<game>|<real>|<digest>|<clients>|<epoch>|<blob>
    epoch: schedule entries the client held when it sealed tick (0 at tick 0).
  NGGO|5|<token>|<slot>|<T>|<source>|<epoch>|<start>:<lag>:<pilot>|<mask>|<blob 1>|...|<blob N>
    source: the proposal tick whose blobs follow, or '-' for a gap permit (all
    empty); epoch: entries in force at issue, the newest one follows; mask: two
    lowercase hex digits, bit s-1 = slot s dropped (its blobs empty). Identical
    on every resend. At most about 4,000 bytes.
  NGPING|5|<token>|<slot>|<nonce>  (relay to client)
  NGPONG|5|<token>|<slot>|<nonce>|<held_us>  (client, when it reads the ping)
    held_us: time since the client last found its socket empty, 0 when the
    ping arrived during a blocking receive (while it waits for a permit). The
    round trip lies in [measured-held, measured].
  NGSTOP|5|<token>|<slot>|<tick>  for any tick the client reported.
  NGDROP|5|<token>|<slot>|<tick>  to a dropped client that reports again.

Agreement (fail closed). Relay: an authenticated, well-formed protocol 1-4
report stops the session (lookahead_mismatch_slot_S); a report claiming more
entries than exist (adaptive_epoch_slot_S_tick_T), sealing a tick an entry it
does not hold changes (adaptive_unannounced_slot_S_tick_T), or carrying input
at a quiet tick (adaptive_quiet_input_slot_S_tick_T) stops it. Client stop
reasons: 190 a plan or entry it cannot follow (above native_gate_lookahead_max,
late, out of order, a different copy, no plan), 191 a permit whose source is
not the one the schedule names (or a mask that shrinks), 192 it sealed input at
a quiet tick, 193 the relay dropped it, 194 the plan's pilot delay cannot be
adopted (pilot prediction armed, outside 2..30 or not below the window start)
or a lowering while wire pilot records are armed; 102, 103 and 56 as protocol 4.
The plan's pilot delay replaces the armed one before tick 1 (the probe arms
with kmax+2 at the menu and with gate.adaptive_plan() after a UI reload). Wire
pilot records keep that delay all session, so with them a session change may
only raise k up to pilot-2 (headroom) and never lower it (194); player orders
keep their configured delay, which the probe requires to be >= kmax+1.

Stalls. --stall-report-ms (1000): NATIVE_GATE STALL slot=S tick=T when the
others have waited that long for S's report of the next tick (also in the
report's adaptive.stalls). --stall-drop-ms (0 = never): past it the relay drops
S from that tick: its later blobs are empty, the mask names it, digests are
compared among the others, it gets NGDROP; the others go on. Slot-bound inputs
(pilot records of S's ship) then miss and stop the session (91) until drop and
rejoin (roadmap D15) give a dropped slot's ship a defined state.

Lua surface. gate.lookahead_adaptive(kmax) after gate.wire(3, N), before
start/boot (1..8; once started only the same value); gate.adaptive_status();
gate.adaptive_plan() -> pilot delay, lag, entries (nil before the plan).
gate.poll(): s.adaptive (entries held), s.lookahead (window of the inputs
taken), s.inputs_tick (their proposal tick; absent for a gap permit), s.quiet,
s.lag (lag of the proposal of s.issued; absent when quiet), s.pilot_delay,
s.dropped. The probe logs ADAPTIVE_PLAN / ADAPTIVE_SCHEDULE once per entry and
ADAPTIVE_STOP <gate.adaptive_status()> at the end. The Linux gate does not
include lockstep_adaptive.h yet and has no gate.lookahead_adaptive: its probe
refuses (REFUSED lookahead=adaptive max=K).

Test links (relay only): --latency-jitter-ms J adds a uniform 0..J/2 per
datagram and direction (datagrams may overtake each other), --latency-spike
PERIOD_S,DURATION_MS,EXTRA_MS a periodic extra round trip, --latency-seed the
draws. With any of them (or --latency-ms) the relay polls its socket and sleeps
in steps of at most 1 ms: Windows rounds socket timeouts to its 15.6 ms timer,
which had made --latency-ms 100 a 125 ms round trip.
WIRE CRYPTO (1 NOVEMBER 2026, OPT-IN)
Why: protocols 1-4 are plain UDP authenticated by one session token. Anyone on
the path reads every input and the token; anyone holding the token (every
player) can send reports as any slot. Design, threat model, costs and the
live-test spec: reports/LOCKSTEP-WIRE-CRYPTO-20261101.txt.
Default off. Protocols 3 and 4 only. Both ends must be switched on:
  relay  native_gate_relay.py --wire-crypto KEYFILE [--wire-crypto-lib PATH]
  probe  X4LAN_CONFIG.native_gate_wire_crypto = "x4c1:<relay key>:<slot psk>"
         (64 lowercase hex each; a secret, never logged)
Keys (tools/dev/native_gate_crypto.py; keep key files under .local/):
  keygen --out FILE        relay key file: Ed25519 seed of the relay and a psk
                           master (32 random bytes each); never overwritten
  credential --key FILE --token T --slot K
                           slot K's string: the relay's public key and
                           psk_K = BLAKE2b-256(master; "X4MP slot psk v1" |
                           sid | K). A player learns only its own psk.
  sid = the 16 bytes of the session token (no longer sent in the clear).
Primitives: Monocypher 4.0.2 (third_party/monocypher-4.0.2): ChaCha20-Poly1305
(RFC 8439), Ed25519 with SHA-512 (RFC 8032), X25519 (RFC 7748), BLAKE2b (RFC
7693). One C implementation (src/native/engine/lockstep_wire_crypto.h) serves
both gates and, through x4mp_wire_crypto (lockstep_wire_crypto_lib.c, ctypes),
the relay. Every name below is a 16-byte zero-padded domain string.

Handshake (first gated frame, before the report of tick 0):
  HELLO   (88, unsealed, resent every 100 ms until WELCOME)
    "X4H1" 01 slot N k | X25519 ephemeral public (32) | the player's Ed25519
    public key (32, fresh per session) | BLAKE2b-128(psk; "X4MP hello v1" |
    sid | HELLO[0..72))
  WELCOME (104, unsealed)
    "X4H1" 02 slot N k | relay X25519 ephemeral public (32) | Ed25519 signature
    of the relay over "X4MP welcome v1" | sid | HELLO | WELCOME[0..40)
  keys = BLAKE2b-512(psk; "X4MP keys v1" | sid | HELLO | WELCOME | X25519
    shared secret): base keys player->relay (first 32) and relay->player.
  NGKEYREQ|1|<token>|<slot>  (sealed, resent every 100 ms until NGKEYS)
  NGKEYS|1|<token>|<slot>|<generation> NUL group key (32) | the N players'
    public keys in slot order. Sent once every slot finished its handshake.
  Both steps must finish within the gate timeout, else stop 107. The relay
  refuses (silently) a HELLO with a wrong MAC (another slot's psk, another
  session), another N or k, a taken slot or address, a public key already in
  the roster; an identical HELLO from the same address gets the same WELCOME.
  The player ignores a WELCOME not signed by its pinned relay key and stops
  (106) on an NGKEYS without its own key at its slot or with a repeated or
  zero key.

Sealed datagram (every datagram after the WELCOME, both directions):
  "X4C1" channel sender receiver generation | counter (8, LE) | ChaCha20-
  Poly1305 ciphertext | tag (16). 32 bytes overhead. Channel 1 player->relay,
  2 relay->player, 3 peer link; sender/receiver 0 = relay, 1..8 = slot.
  Nonce = header bytes 4..15; additional data = sid | header. Subkey per epoch
  of 65,536 counters: BLAKE2b-256(base; "X4MP subkey v1" | header[4..8) |
  epoch). The receiver drops a counter it saw or one 1,024 below the highest;
  only an authentic datagram moves that window. A sender never reuses a
  counter (each resend is sealed anew).
  Plaintext = the protocol 3/4 ASCII datagram unchanged; reports and permits
  add a NUL and a binary trailer:
  NGSTATE|3/4 ... NUL sig (64): the player's Ed25519 signature of its input
    record "X4MP input v1" | sid | slot | N | k | 0 | tick (8, LE) | blob
    length (2, LE) | blob bytes. Empty blobs are signed too.
  NGGO|3/4 ... NUL sig_1 .. sig_N (the records of tick T-1-k; 64 zero bytes
    each for T <= k) | the relay's signature over "X4MP permit v1" | sid |
    T (8) | N | k | 0 0 | T-1-k (8; all ones for none) | BLAKE2b-256(
    "X4MP records v1" | per slot: blob length (2) | blob | sig).
  Sizes: a report grows by 65+32 bytes (largest 746 sealed), a permit by
  64*(N+1)+1+32 (largest, N=8, 4,521 sealed): inside GATE_STATE_MAX and
  GATE_PERMIT_MAX.

Checks and failures (fail closed):
  Relay: drops unsealed datagrams, unknown senders or addresses, forged and
  replayed datagrams and reports naming another slot (counted in the report);
  a report whose record signature fails (or is missing) stops the session:
  wire_crypto_signature_slot_S_tick_T, NGSTOP to every client.
  Gate: drops what is not authentic or is a replay (counted); verifies every
  other slot's record and the relay's signature in every permit (an identical
  copy of a verified permit is not verified twice). An authentic datagram with
  invalid content (a bad signature, a permit without its trailer, an
  unexpected format, a changed roster) stops with 106. Start/boot return 10
  when wire crypto is armed without protocol 3. The portable and GetUp
  transports are refused (106) while armed.
  New stop reasons: 106 invalid authentic content, 107 handshake or keys not
  completed within the gate timeout.

Lua and logs:
  gate.wire_crypto(credential) -> 1 or 0: after gate.wire(3,N) (and
    gate.lookahead), before start/boot; once started only the identical
    credential returns 1 (UI reloads). Runs the RFC known answers first.
  gate.wire_crypto_status() -> "armed= established= keyed= establish_ms=
    hellos= keyreqs= reports= sign_us= permits= cached= records= verify_us=
    opened= forged= replayed= dropped= sealed= stop= key= roster=" (sums in
    microseconds; key = this client's Ed25519 public key, roster = BLAKE2b-128
    of the N keys, the relay report's roster_fingerprint).
  The probe adds " wire_crypto=1" to ARMED, logs WIRE_CRYPTO_KEYED key=...
  roster=... once keyed (players compare these out of band: a relay that
  substituted a key shows a different roster on some client) and
  WIRE_CRYPTO_STOP <status>.
  Relay: prints NATIVE_GATE RELAY WIRE_CRYPTO relay_key=<hex> before READY;
  the report adds "wire_crypto" (relay key, players' keys, roster fingerprint,
  counts, seconds, failure); with --input-journal each line adds "sigs"
  {slot: signature}, so every released record stays verifiable afterwards.
  --wire-crypto refuses --live-inputs (protocol 2 commands).

Peer links (B6; lockstep_wire_crypto.h, x4c_peer_* in the library):
  wc_peer_key(group, sid, generation, sender): sender s seals under its own
    subkey of the group key, receiver 255 (one datagram for every peer).
  wc_peer_seal(tx, sid, own Ed25519 secret, N, k, tick, blob): plaintext
    slot N k 0 | tick (8) | length (2) | blob | the record signature.
  wc_peer_open(keys[N], roster[N], sid, N, k, datagram): 1 an authentic
    record (slot, tick, blob, signature); 0 not authentic (outsider); -2
    authentic under the group key but the record or signature is wrong (a
    player holding the group key forged it: keep as evidence, never apply).
  Replays are the caller's: a record is idempotent per (slot, tick); accept
  only ticks not yet run and inside the permit window; two different validly
  signed records of one (slot, tick) prove that player equivocated. The same
  record signature is what the relay forwards in NGGO, so a peer copy and the
  relay's bundle can be compared byte for byte.
  wc_seal/wc_open, wc_record_sign/verify and wc_permit_sign/verify are the
  single-record primitives behind all of the above.

PEER LINKS: EXTENSION 1 OVER PROTOCOL 4 (1 NOVEMBER 2026, OPT-IN)
Why: with the relay alone, every client's own report makes the relay round
trip before the permit that carries it comes back, so the round trip r to the
relay is paid even by a player sitting next to it, and the slowest client sets
P = max(f, (r+f)/(k+1)) for everyone. With peer links each client also sends
its sealed proposal straight to the other players; the step cycles then run
through the pairs (one-way latency p between two players) and the relay may
lag up to m more ticks: P = max(f, (p+f)/(k+1), (r+f)/(k+m+1)). Inputs still
apply at t+1+k, so the input delay is set by the peers, not by the relay.
Measurements and the go/no-go: reports/LOCKSTEP-PEER-LINKS-20261101.txt.
Off unless every PC sets native_gate_peer_window = m and the relay runs with
--peer-window m; nothing below exists otherwise (every packet unchanged).

Rules (k = protocol 4 window >= 1, m = peer window, k + m <= 8):
- A record sealed with tick t (the NGSTATE blob) is sent once to every peer
  the NAT module reaches and applies at T = t+1+k, exactly like the permit.
- F is the highest tick whose relay permit, and every earlier one, arrived.
  Any tick T runs only when T <= F + m: on its relay permit as before, or
  without it on all N records of T-1-k (and only once F >= 1, i.e. the relay
  admitted tick 0 for every client, and never past the relay's last tick).
  m = 0 exchanges and checks records but runs only on permits (measurement).
- Every relay permit is compared with the peer copies of its records, before
  or after its tick ran. A peer copy that differs stops the client (104), two
  different peer copies of one record stop it (108), another copy of a final
  permit stops it (103); the client first tells the relay (NGPFAIL), which
  fails the session and sends NGSTOP to everyone. Malformed, unauthenticated
  or unexpected peer datagrams are dropped, never fatal. The relay stays the
  referee: digests, clocks, timeouts, the session end; a stopped session ends
  with clients up to k+m ticks past the failing tick (protocol 4: k).
- A client whose peer records are missing (lost, pair unreachable) simply
  waits for the permit, as in protocol 4. While waiting it resends its
  reports from F-k (the report that releases the missing permit F+1).

Messages (ASCII, '|'; the relay port; peer sockets are a second UDP socket
per client, bound to loopback for a loopback relay, else to any address on
the NAT module's port):
  NGPHELLO|1|<token>|<slot>|<clients>|<k>|<m>      peer socket -> relay
    the client's opt-in, every 100 ms until answered. The relay keeps the
    first address it sees per slot, only from the host the slot's reports
    come from, and answers nothing until every slot said hello.
  NGPADDR|1|<token>|<slot>|<m>|<last>|<ip:port 1>|...|<ip:port N>
    relay -> each peer socket, once all N opted in (and to every later
    hello): the peer socket address the relay saw for every slot (NAT
    mappings; own entry included) and the last tick (--ticks).
  NGPREFUSE|1|<token>|<slot>|off|mismatch           relay -> peer socket
    no --peer-window, or another N/k/m: the client stays relay-only.
  NGPREC|1|<token>|<slot>|<tick>|<clients>|<k>|<blob>|<signature>
    peer socket -> peer socket, the whole datagram sealed by the crypto
    module; signature over everything before it (empty with the stub).
    Accepted only from the address routed for that slot.
  NGPFAIL|1|<token>|<slot>|<tick>|<103|104|108>     relay connection -> relay
    the session fails (peer_link_stop_<reason>_slot_<S>_tick_<T>) and every
    client gets NGSTOP for the newest tick it reported.
The relay with --peer-window m accepts reports up to m ticks past its newest
permit (a client runs at most that far ahead of it). Its report and status
add "peer_window" and "peer_links" (waiting/exchanged), never an address.
An older relay drops NGPHELLO: the session then runs relay-only.

Privacy. Players learn each other's IP addresses (and the ports of the peer
sockets). Hence: off by default, opt-in per PC (native_gate_peer_window) and
per session (relay --peer-window), and all-or-nothing: the relay hands out no
address unless every client opted in. Records travel in clear text with the
stub crypto module, like the relay path without wire crypto.

Native surface (lockstep_peer.h, shared by both gates; status for the probe):
gate.peer_links(m[, P]) -> 1/0  m = 0..8-k after gate.lookahead(k >= 1), -1
                                 off; P the relay's NGNAT rendezvous port
                                 (1024..65534) or nil/0; before start/boot,
                                 then only the same m and P
gate.peer_status() -> "peer=<off|hello|active|refused|failed> window= sent=
  received= peer_runs= peer_first= relay_first= lead_us= behind_max= final=
  last= dropped= duplicates= stale= unreachable= crypto=<stub|wire>
  nat=<stub|traversal> forged="
  (peer_runs: ticks run on peer records without the permit; peer_first /
  relay_first: ticks whose N peer records were complete before / after the
  permit; lead_us: summed head start of the peer records over the permit;
  behind_max: farthest a tick ran past F)
Probe: X4LAN_CONFIG.native_gate_peer_window = m (needs native_gate_lookahead
k >= 1, k + m <= 8); the ARMED line adds " peer_window=m", the end logs
"NATIVE_GATE PEER_STOP <gate.peer_status()>"; a DLL without gate.peer_links
refuses (REFUSED peer_window=m). Stop reasons 104 and 108 are new (108 was
105 on the branch; 105 is the Linux gate's; docs/LOCKSTEP-REGISTRY.txt).
Interfaces of the NAT and crypto modules: peer_nat_api {local_port, route
(slot, advertised address -> route, unreachable or pending), datagram (their
own probes)} and peer_crypto_api {seal, open, sign, verify}; the stubs stay in
lockstep_peer.h and tools/dev/native_gate_peer.py for sessions without the
real modules. Joined at the integration (1 November 2026):
- NAT traversal: gate.peer_links(m, P) / native_gate_peer_rendezvous_port = P
  with the relay's --rendezvous-port P runs the NAT core (lockstep_nat.h) on
  the peer socket itself (NGNAT| datagrams are the core's, from anyone, a
  routed peer too). A slot's route is the core's DIRECT path (authenticated
  nonce round trip); RELAY (no rendezvous, timeout, symmetric pair) is
  "unreachable": that slot's records come only with the permits. NGPADDR's
  addresses are then not used as routes; NGPHELLO/NGPADDR stay the opt-in and
  carry the last tick. Without P the stub routes to the NGPADDR addresses.
  Not joined: UPnP/PCP port mapping (lockstep_nat_portmap.h, blocking, a
  worker thread's job) and the core's CLOSE/BYE at the session end (the
  rendezvous times the entries out).
- Wire crypto: with gate.wire_crypto armed every record is wc_peer_seal (the
  NGKEYS group key, the sender's subkey, the record signed with the player's
  session Ed25519 key: the signature the relay checks on its report) and only
  wc_peer_open's authentic record of the routed sender is taken (forged=
  counts a group key holder's forgery). Nothing is sent before NGKEYS and
  nothing in the clear; NGPFAIL goes sealed. Not built: the relay's sealed
  NGPHELLO/NGPADDR, so the relay refuses --peer-window with --wire-crypto
  and a crypto client stays relay-only (peer=hello) against any relay.
- Protocol 5 (adaptive) has no peer links: gate.lookahead_adaptive refuses
  after gate.peer_links and the gate's start refuses both (10); the probe and
  the relay refuse the combination too.

INPUT MULTIPLEXER (tools/dev/native_gate_inputs_core.lua, 29 October 2026)
The probe's own inputs share one blob per slot and tick: pilot records (wire
source), player orders and hit claims register as sections of the
multiplexer, which is then X4LAN_NATIVE_INPUTS (owner 'mux'). An external
adapter that is not the multiplexer still owns the wire alone (unchanged).
Blob format: the container of src/native/engine/lockstep_hit_claims.h
(input_mux_decode/encode): '' = no input; 28 bytes starting 0x01 = pilot
record alone; starting 0x50 = orders alone (both legacy forms, byte-identical
to the former exclusive adapters); otherwise 'M' 0x4d, version 1, sections
kind|length|payload in ascending kind order (0x01 pilot, 0x48 hits, 0x4f
octree, 0x50 orders). A container holding only a channel with a legacy form
is refused (hits or octree alone use the container).
Section adapter contract (per section, owner tag; same owner may replace):
  apply(tick, inputs, clients, slot) -> receipt string or nil
    inputs[1..N] = this section's payload of every slot, '' when absent or
    when that slot's blob was refused.
  proposal(tick, budget) -> payload or nil
    budget = hex characters left in this slot's blob for the section.
  refused(tick, reason) optional: the payload was dropped ('overflow').
Proposal rule (local, deterministic): sections in priority order (default
pilot, orders, hits, octree; native_gate_input_priority lists pilot, orders
and hits, octree optional and last when omitted), each offered the bytes left
after the container header and earlier sections (2-byte section headers);
a payload larger than its budget is refused for this tick and logged
(INPUT_MUX_OVERFLOW), later sections are still offered. 240 bytes per blob.
Admission (every client): a blob that does not decode, or holds a section no
adapter registered, gives that slot no sections (INPUT_MUX_REFUSED); the
digest gets INPUTS_1|tick|<slot rows>|<section>:<slots present>/<bytes>|
<section receipt or ->... for every registered section in kind order.
native_gate_hit_claims = 'carry' registers a carrier for scripted claims
(native_gate_hit_claims_script) that folds admitted claims into HITS_1
receipts and never applies a hit. Report: LOCKSTEP-INPUT-MUX-20261029.txt.
true/'shooter'/'victim'/'first' register the native 'hits' section with the
pilot section instead: its apply stages every slot's payload
(gate.hit_claims_admit), pilot_frame resolves the claims due
(gate.hit_claims_resolve), its proposal returns this client's queued claims
within the budget (gate.hit_claims_proposal); see
reports/LOCKSTEP-HIT-CLAIMS-NATIVE-20261029.txt.
native_gate_nav_octree = 'agreed' registers the 'octree' section (kind 0x4f,
exactly 20 bytes): proposal = gate.nav_octree_report() (W u32 little endian,
the first octree index not built on this client, then 128 bits for
W+1..W+128; nil when every index is shown), apply = gate.nav_octree_agree(
tick, clients, payloads joined by ','), receipt OCT_1|tick|shown|agreed|
assigned|keys. Reports are cumulative, so the section is offered last and a
full blob only delays it a tick (lockstep_nav_octree.h).
