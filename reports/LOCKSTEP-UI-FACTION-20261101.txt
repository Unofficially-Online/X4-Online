2. RULE IDS: HOW X4 ALLOCATES THEM AND WHY THEY ARE THE SAME EVERYWHERE [F]
  - Three world managers (pointers): blacklists [0x6cf1850], fight rules [0x6cf1878], trade rules [0x6cf17d8]. A create takes
    ++counter, the manager's first dword, as the new ID: 0x371370 (`inc dword [rcx]`, CreateBlacklist2 -> 0x371370 with
    g_PlayerFaction as the owner), CreateFightRule inline at 0x179285 (owner g_PlayerFaction stored at the rule's +0), 0x807760
    (CreateTradeRule; owner g_PlayerFaction at +0). The other callers of the two create functions are CreateBlacklist (v1, no
    stock menu calls it), SetContainerBuildAllowedFactions (0x1dc2a0, no stock menu calls it) and 0x11c7810 (not a UI path [I]).
  - The rules sit in a tree per manager: header at +0x10 (+0x18 root, +0x30 leftmost, +0x38 count), node +8/+0x10 children,
    +0x20 the ID, +0x28 the rule, the rule's +0 its owner faction (the listers 0x371280 / 0x807670 and the lookups of
    RemoveBlacklist / RemoveFightRule / RemoveTradeRule read exactly these; all pinned). A remove erases the node and
    decrements the count (0x371580, 0x808d60, 0x807930); the counter never goes back.
  - So: the save gives every client the same counters; the simulation's own creates (if any) run in the simulation alike; the
    replayed creates run in the probe's frame in the same order everywhere -> the same IDs. The receipt carries each counter
    and size: a create that took on one client only is a mismatch at that tick.
  - The capturing menu (menu_playerinfo.lua buttonBlacklistConfirm and its fight/trade twins) stores the create's answer as the
    edited rule's ID and sets the defaults with it in the same click; later clicks (confirm again, remove) use the stored ID.
    A predicted real ID could be wrong (another slot's create can apply first), so the answer is a token
    0x7f000000 | slot << 16 | sequence (int32, never a real ID, nonzero so the menu goes on). The record of a create carries its
    token; at the apply every client maps token -> X4's answer (a ring of 256); a later record of any kind naming a token runs
    with the real ID, is skipped `token` when nobody mapped it (another client's sequence, evicted) and `depends` when X4 answered
    0. A record whose token names another slot is malformed (stop). The same on every client: the map is filled at the apply.
  - What the person sees on the capturing client: the edited rule stays on screen with its token until the menu re-reads the
    list (the stock list then shows the real ID); confirming or removing it again works through the token.

3. COOP, FACTIONS, AND WHO MAY CHANGE WHAT
3a The faction scope (reused from lockstep_ui_trade.h uitrade_scope_enter / _leave, its pins checked at this family's arming):
  every record of slot k runs with g_PlayerFaction = the owner of slot k's ship (coop and slot 1: `player`, nothing written).
  [F] what reads g_PlayerFaction: the three creates (the new rule's owner), SetPlayer{Blacklist,FightRule,TradeRule}Default (the
  faction's default table, faction data +0x280 +0x240..), SetPlayerFactionName (0x9d9f00 on g_PlayerFaction), the module pause
  setters (their owner check [I]). The scope's counters (scopes= in UI_TRADE_STATUS when trade is armed) count both families.
3b Faction ID arguments [F]: SetFactionBuildMethod, SetFactionDefaultWeaponMode, SetDefaultResponseToSignalForFaction2 and
  ResetDefaultResponseToSignalForFaction look the faction up by name in g_FactionDB (FNV-1a of the ID), so "player" is the
  real player faction whatever g_PlayerFaction is. The run rewrites "player" to the slot faction's ID (the Lua half reads it
  from the slot ship's owner; the native half stops with ui_faction_view if that reading and the scope disagree); any other
  faction ID is refused not_owner. "player" inside a blacklist's, fight rule's or trade rule's faction list becomes the slot
  faction too (the stock menu shows `player` as "your faction"); other faction IDs in the lists are kept.
3c The player entity's settings [F]: SetPlayerShipsWaitForPlayer, SetPlayerTaxiWaitsForPlayer, SetPlayerGlobalLoadoutLevel and
  SetPlayerTradeLoopCargoReservationSetting write [[0x3d198f8]+0x230] +0x8a6b4 / +0x8a6b5 / +0x8a6a8 / +0x8a720;
  SetPlayerIllegalWare its ware set (+0x8a6d0); SetPlayerPaintTheme / ClothingTheme call the entity (0x70a720 / 0x70a910);
  SetPlayerLogo writes the logo into the entity's owner faction (vfunc +0x1610, `player` for X4's player). The canonical apply
  changes X4's own player, the one the simulation reads; none of these fields is in the slot store (lockstep_virtual_players.h),
  so every client's menu shows the shared value. Coop: every slot changes them (shared). Factions mode: x4lan_playerk has no
  entity the simulation reads for its ships [I], so slots 2+ are refused at capture (UI_FACTION_REFUSED why=player_entity, the
  info line, nothing on the wire) and a record that arrives anyway is skipped everywhere. With
  native_gate_player_settings_per_slot every slot k has and changes its own values instead: section 13.
3d Authority, at the apply on every client (the world is the same, so is the verdict):
  rule IDs (native): a positive ID must name a rule of the slot's faction (not_owner; gone when no such rule; -1/0 pass as the
  menu passes them: "the controllable's own setting off").
  component subjects (Lua, as the trade family): the slot needs a ship (no_ship); the subject must not be another slot's ship
  (slot_ship) and must be owned by the slot's faction (GetComponentData owner; not_owner). The own ship is allowed.
  So coop: any slot edits every `player` rule, station, module and non-slot ship; factions: slot k only x4lan_playerk's.

4. FACTIONS MODE: THE FACTION VIEW (client k's own UI only)
  The stock queries the player information menu uses read g_PlayerFaction [F]: GetAllBlacklists 0x1808d0 / GetAllFightRules
  0x182970 / GetAllTradeRules 0x1836f0 list g_PlayerFaction's rules (the listers of section 2), IsPlayer*Default read its
  defaults, GetPlayerFactionName and GetPlayerMoney its name and account. Without a view client k would list slot 1's rules
  (and every edit of them would be refused not_owner).
  Built: gate.ui_faction_view(1/0) opens g_PlayerFaction = this client's slot faction around a stock Lua function, only on the
  UI thread in a local phase (uirep_local_phase), never in an apply, a trade scope or a slot scope, never when this slot's
  faction is the player faction (coop, slot 1: answers 0); nested calls keep the outer view (2); a close finds g_PlayerFaction
  as it was opened (else the replay stops, 164, ui_faction_view); a pass never finds it open (ui_faction_view_open); an apply
  inside it stops. The capture's entity rule still uses the true player faction. The Lua half wraps, once each exists:
  PlayerInfoMenu.onShowMenu / refreshInfoFrame / onUpdate (the info frame and its empire tab: lists, details, defaults, name,
  money, settings) and Helper.getBlackLists / getFightRules / updateTradeRules (also the map's rule dropdowns). Click handlers
  are not wrapped: what they change is captured as above. Rows: UI_FACTION_VIEW_WRAPPED, views= in UI_FACTION_STATUS.
  (Section 13 corrects and closes this paragraph: the build method is read through g_PlayerFaction [F GetPlayerBuildMethod
  0x1d73b0], so the view already shows slot k's; the four getters by faction ID are rewritten with the key.)
  Not in the view (read by faction ID "player", so they show `player`'s values on client k): the default responses to signals
  (GetDefaultResponseToSignalForFaction2(..,"player",..)), the default weapon mode, the build method. Changing them works (the
  apply rewrites "player"); the menu shows slot 1's value until a view for faction-ID queries exists (native query hooks).

5. NATIVE AND LUA DETAILS
  Wire: op 0x5a (Lua-run), one record per claimed call: claim | token (creates) | arguments by spec; strings with a length byte
  (<= 254, 0xff = NULL), arrays <= 255 entries, a record <= 24 parts of 197 bytes, all parts or none (queue room checked first;
  a part refused midway is a torn record: dropped on every client). Section rule: the family armed, index < count <= 24.
  Apply: gate.ui_faction_part(slot, hex) reassembles per slot and walks the whole record (malformed: stop 164,
  ui_faction_record); then the Lua half checks the subject and calls gate.ui_faction_run(slot, slot faction ID, verdict): the
  component resolved (gone: skip; identities differ: stop ui_ref_mismatch), the faction relation (ui_faction_view on a
  disagreement), the entity rule, faction IDs, rule IDs (tokens, owners), the scope, X4's function through its entry (the guard
  passes an apply; a fault stops ui_fault with the scope closed), the token mapped, the hash folded.
  Receipt (joins the pilot receipt through S.extras): |UIFAC_1:b<counter>.<size>,f..,t..;<slot 1 b.f.t>,<slot 2 b.f.t>;
  w<ships wait><taxi waits><loop reserve>.<global loadout float bits>;h<hash>. 'x' a slot without a faction, '?' a manager that
  cannot be read, 'w-' no player. Read only (guarded reads), in the probe's frame.
  Rows: UI_FACTION_PINS ok=1, UI_FACTION_ARMED slot= families= claims=33 missing=<stock types not declared yet>,
  UI_FACTION_REFUSED tick= op= why= (this client's capture refusals; info line "Multiplayer: <name> is not shared for your slot
  yet - nothing happened." at most every 90 ticks), UI_FACTION_STATE (the receipt without the hash, plus the first signal's
  default response of each slot faction, when it changes), UI_FACTION_STATUS every 120 ticks (captured refused out= in= torn
  ran skipped scopes=opened/same tokens=mapped/unknown views=opened/nested/refused; lua=applied/skipped/parts/dropped/refused
  view=), UI_FACTION_DROPPED, UI_FACTION_VIEW_WRAPPED; UI_REPLAY_APPLIED op=90 what=<name>[ scope][=<answer>] or
  what=<name> skipped=<why>.
  Pins (fail closed, gate.ui_faction_pins before any patch and again at the arming): the two listers, the blacklist create and
  its constructor, CreateFightRule's inline create, the trade rule create, the four entity setters (whole bodies), plus the
  trade family's pins (the scope, GetTrueOwner, the Ship vtable slot). The claimed entries' own pins are the guard's.
  Stop whys (164): ui_faction_not_armed / _need_guard (first pass), ui_faction_record, ui_faction_overlap, ui_ref_mismatch,
  ui_faction_view, ui_faction_rules_unreadable, ui_fault, ui_faction_scope, ui_faction_scope_open, ui_faction_view_open.
