LOCKSTEP STARTS: A SESSION FROM ANY USABLE STOCK START, A START PER PLAYER - 1 NOVEMBER 2026
Branch contrib/ferrite-starts (from smoke d9c299dd). Offline design, code and tests: Python, LuaJIT,
synthetic stock data and synthetic clients; both MD files validated against the game schema. No X4 run,
no lane, no native change. Section 9 has the live tests for the coordinator, section 10 the people checklist.

USER REQUEST (1 Nov): "multiple starts working": (1) a session can begin from any stock X4 game start, not only
the creative test save; (2) each player can choose their own start (faction, ship, location, money, blueprints,
inventory, reputation), all in one shared universe. Coordinator addition: some starts change the world (the start
with a station); catalogue every start by what it touches, three classes enforced in code, refuse loudly, never
apply a start in part, say which per-player effects come from MD and whether they are replayed or refused.

1. A SESSION FROM A STOCK START: HOW EVERY CLIENT GETS THE SAME WORLD
Option A, every client runs X4's own new game for start S with the same seed, the gate armed from the first frame:
  refused. Evidence: reports/SHARED-START-20261023.txt, two fresh native worlds with seed 276944566 made 1381 and
  1382 stations, 46/47 station identities absent/extra while 1335 tuples agreed. New-game generation (god placement,
  job spawns, the start's own MD) runs during the load, before any gated tick exists (the gate admits ticks after
  the boot hold of a loaded save), on worker threads and wall-clock time slices; and the census still sees an
  intermittent load-time class on a loaded save (docs/LOCKSTEP-SCENARIOS.txt, sc-control tick 2). A census could
  measure A, but it would have to make a generator deterministic that the gate never sees.
Option B, one process makes the new game for S once, saves it, every client loads that save: RECOMMENDED and built.
  It is today's proven snapshot path (native_gate_lane.py --snapshot-in, native_gate_snapshot_sha); only the save
  differs. Whatever the start's new-game MD and god.xml did ran once, in one process, and is in the save.
Tooling (tools/dev/native_gate_session_start.py, uses native_gate_scenarios.py capture/rebase):
  spec             --base-start S --players N --mode M [--start K=ID ...] [--omit K=PARTS ...] -> spec.json
  capture-overlay  X4's new game for S (battle MD copy whose only change is the gamestart guard, the snapshot
                   script), the 12-ship battle fixture (the census anchor every full-stack overlay needs:
                   native_gate_hash='battle', snapshot_fixture enrolment), and one hull per per-player start
                   (section 5); prints the one-lane capture command (expects GAMESTART id=S, HULLS_READY)
  register         reads the captured save read-only: header start == S, seed, player ship and sector, the
                   fixture (Spawn.$ships), the hulls (X4LAN_SessionHulls.Create.$ships, each checked for macro,
                   owner player, zone and sector of its start); sha256 -> session.json
  rebase           binds a full-stack overlay to the session save (snapshot sha, fixture, watch list)
  native_gate_players.py --session session.json then replaces every snapshot-005 default (player ship, fixture
  actors, sectors) with the session save's and puts the per-player starts into the identity plan (default on);
  it refuses a base overlay that boots another save ("rebase it"), another player count or mode than the spec,
  and wire/script piloting of hulls (no Steering solver; stock or none).
What makes a start usable as the session base (native_gate_gamestarts.session_base_refusal, enforced by spec):
  not refused (section 2), the player in a ship (not a spacesuit) in open space of the main galaxy (the capture
  warps player.ship to 0/100 km/0 of its sector and spawns the fixture there: the base start keeps its sector,
  not its exact position), no fullscreen intro the capture cannot pass (boron1, pirate1: observed earlier).
  Class b starts ARE allowed as the base: their world parts are in the save every client loads.
  Usable today: custom_creative, custom_budgeted, x4ep1_gamestart_fight, _discover, _split2, _terran1,
  _hyperion, _dlc_mini_02 (the last two untested by any capture). Not: docked or on-foot starts (trade,
  scientist, boso, intro, tutorial, terran2, pirate2, boron2), the spacesuit start split1.

2. CATALOGUE OF EVERY STOCK START (tools/dev/native_gate_gamestarts.py catalog)
Read at setup from the game's own data, never copied into git (--libraries/--scripts or X4LAN_GAME_LIBRARIES /
X4LAN_GAME_SCRIPTS: the resolved per-extension layout, base + ego_dlc_*; other mods are not read):
  libraries/gamestarts.xml of the base game with every stock extension's diff applied (own reader of the stock
    diff subset: add/replace/remove, [@a='v'], [n], comment()[. = 'text'], @attribute; an unknown selector, an
    unmatched non-silent operation or a selector matching several nodes is an error, never skipped);
  god.xml entries that exist only for one start (quota gamestart="<id>", <gamestart ref>);
  MD and AI scripts keyed on the start: a cue with module="<id>" (its whole subtree) or a player.module == '<id>'
    test (its cue). player.module != '<id>' runs for every other start, so it is not a part of <id>.
Parts: player-level = ship + loadout, position, money, inventory, blueprints, research, reputation toward NPC
factions (universe relations with the player). World-level = another galaxy, a start location in a player-owned
station, god.xml stations/products of the start, universe god/jobs/masstraffic settings, relations between NPC
factions, custom-editor blocks (stories, known space, people, stations), known space, and every start-keyed MD
cue that does more than structure/logging. Presentation only (listed, not applied): info, cutscene, intro, type,
loading screen, unlocks, the player's paint theme and timeline, encyclopedia entries, character macro and name.
Unknown parts (e.g. loadout ref, ship modification/people) count as world parts: what the reader cannot name is
not applied per player.
Classes (enforced in code: classify, per_player_refusal, session_base_refusal, slot_kit):
  a  per-player safe: player-level parts only
  b  session base only: at least one world part. Only slot 1's (the save's) start; a per-player choice is refused
  c  per-player with world parts rebuilt deterministically, each listed and applied by the identity plan at the
     same tick on every client, never by running the start's own new-game MD. Rebuilt today: a start cue whose only
     effect is the stock map uncover (md.LIB_Generic.UncoverMap_SectorsAndGates) with a literal sector list
  -  refused: tutorials/no-save/hub/station designer (tags), debug and test starts, Timelines scenarios, another
     galaxy, the two fullscreen-intro starts

4. WHO PLAYS WHICH START
Slot 1 plays the session base start S: the singleton player, its ship, money, reputation, blueprints and map are
the save's. Slots 2..N each choose a class a or c start (spec --start K=ID); a class b start can only be chosen as
the base (spec --base-start). So "each player chooses a start" = slot 1 picks S, the others pick per-player starts.

5. PER-PLAYER STARTS: HULL IN THE SAVE, KIT AT THE SETUP TICK
Ship + loadout + position: pilot slots need saved IDs fixed before the load (pilot manifest), so a ship created at
the setup tick could not be flown. The capture therefore creates slot k's HULL once, in the session save: the
start's ship macro with its stock loadout (create_loadout: engines/weapons/shields/turrets with their connection
paths, ammunition, software, thrusters), at the start's zone position (find_zone of the start's zone macro, the
stock position and yaw; slots taking the same start are 300 m apart on x), owned by the player, an Argon AI pilot,
default Wait, fixed seed 5100+k (generated MD x4lan_session_hulls.xml, overlay only). register checks each hull.
At the setup tick the identity plan's existing ship step takes the hull over (coop: unchanged/player; factions:
x4lan_player<k> with overridenpc), no start placement is needed.
Everything else is the plan key "kits" (identity plan format v1, optional; plans without kits keep their text and
digest), applied by MD on every client at the same gated tick after the relations:
  part         coop                                         factions (slot k = x4lan_player<k>)
  money        ADDS to the one shared wallet (step wallet    SETS slot k's own account (wallet op=set: reward the
               op=add): shared = base start money + sum of   delta to the player, transfer it to x4lan_player<k>;
               slots 2..N's start money                      the player's wallet is read back unchanged)
  reputation   one reputation set (the base start's):        slot k's faction toward each NPC faction of the start,
               must be omitted                               both directions, after the mirror (step reputation)
  blueprints   added to the one player library (per ware)    X4 keeps blueprints for the player faction only: omit
  research     added (per ware)                              player faction only: omit
  map uncover  the start's sectors (class c): known_sector    player faction's knowledge only: omit
               per sector, then known runs the stock library
  inventory    the player entity P_k of slot k is not reachable from MD (lockstep_pilot_slots.h): omit (both)
  presentation not applied, listed by spec (encyclopedia, paint theme, character, intro)
A part that cannot be applied must be named in --omit K=parts; without it the start is refused naming slot, start,
mode and parts ("parts blueprints, inventory, known, research cannot be applied for slot 2 in factions mode; name
them in --omit 2=... or choose another start"). The omitted list is in the plan text and in the kit step's
APPLIED line (omitted=...), so a left-out part is never silent. An applicable part may be omitted on purpose.
Kit rows: {slot 2..N, gamestart, money (credits, 0..1e12), reputation [{faction, value: millionths}] (factions),
blueprints/research [ascending wares] (coop), known {sectors, faction?, shipyards} (coop), omitted [ascending]}.
Lua (native_gate_player_identity_core.lua K.kits) and Python refuse the same kits with the same reason: kits,
kit_invalid, kit_slot, kit_duplicate, kit_player_slot (factions: the player faction's start is the base),
kit_gamestart, kit_money, kit_reputation, kit_reputation_mode, kit_faction, kit_value, kit_order, kit_wares,
kit_ware, kit_library_mode, kit_known, kit_known_mode, kit_omitted, kit_omitted_conflict, key_unknown.
Canonical text: ...|kits=<k>:<gamestart>:money=<m>:rep=<f>/<v>+..:bp=<w>+..:rs=<w>+..:known=<faction|->/<0|1>/
<sector>+..:omit=<part>+.. (rows by slot, ';'). Steps per kit: kit, wallet, reputation*, blueprint*, research*,
known_sector*, known. MD results (one APPLIED line each): wallet applied|unchanged|refused_wallet_invalid|
refused_wallet_readback (money=<account> player=<wallet> or money=<shared> before=<old>), reputation applied|
unchanged|refused_relation_readback (ab= ba=), blueprint/research applied|unchanged|refused_*_readback|
refused_ware_invalid, known_sector applied|refused_known_invalid (count=), known applied|unchanged|
refused_known_readback (known=<now>/<n> before=<was>). Any refusal stops the session at the fold tick (as before).

8. WHAT WORKS / WHAT REMAINS
Works offline: catalogue and classes of every stock start, refusals naming start and parts, session spec, capture
overlay with hulls, register, rebase, builder --session, kits through the real Lua core/glue and MD validated
against the schema. Not run natively (all of section 9 is pending). Assumed, read back at run time:
  - reward_player with a negative amount (the factions wallet when an account holds more than the start's money;
    pool accounts start at 0, x4lan_trade.xml uses the same pattern), transfer_money into a faction account,
    player.money/faction.money read back in the same action block;
  - player.blueprints.{ware}.any.exists and ware.research.unlocked as readbacks (stock idioms);
  - the stock map uncover called from our MD with our list; sector.isknown as its readback;
  - a created hull (stock gamestart loadout via create_loadout) has a cockpit X4's stock control path can seat
    P_k in (the snapshot-005 stock slots were scouts with working cockpits; a fighter fixture showed a flat panel).
Open:
  - inventory of slots 2..N (P_k's inventory needs a native step: P_k is not an MD entity);
  - blueprints/research/map knowledge per pool faction (factions mode): X4 keeps them for the player faction only;
  - class b per-player starts (station start: section 3); on-foot and docked starts as base or per player;
  - the base start's exact stock position (the fixture capture warps player.ship to 0/100 km/0 of its sector);
  - a fixture-free session save (the census stack is anchored on the 12-ship fixture today);
  - hulls in more sectors than are covered: the builder's sector check applies (two sectors, or view scenes);
  - presentation parts (paint theme belongs to lockstep_player_settings.h; encyclopedia, character).
