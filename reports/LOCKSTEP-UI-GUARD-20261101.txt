LOCKSTEP UI GUARD: CONTAINMENT FOR STOCK UI ACTIONS NOT REPLAYED YET, AND THE FIRST P3 STEP
1 November 2026 | offline work on branch contrib/ferrite-ui-guard (base: smoke 0875790b). Static analysis of the pinned Windows
X4.exe 9.00 (RVAs, base 0x140000000) and of the extracted stock UI and MD scripts, read locally in x4-re; nothing of them is
copied here (names of API functions, script files and RVAs only). No X4 was launched.
[F] = read in the binary or the scripts; [I] = inference; "live" = what only a native run can show.
Builds on reports/LOCKSTEP-UI-REPLAY-20261030.txt (the replay, its local phases, its families, its inventory).

0. PROBLEM AND RESULT
  Two people in the people config (overlay-Play42P) can still split the session with UI actions the replay neither replays nor
  refuses: conversations, AddUITriggeredEvent, SignalObject*, missions, trade, construction, crew and assets. Each runs only on the
  client that clicked; MD then runs on one client, the next shared runtime ID parts, the world diverges.
  Built (all default off):
  - native_gate_ui_guard = 'all' (or a list of groups): in the replay's local phases every world-changing stock UI entry point of
    the inventory that no armed family captures is refused: the function does not run, it returns its failure/neutral value, the
    refusal is counted by name, logged (UI_GUARD_REFUSED) and shown to the person in X4's own info line. 280 entry points: 225 FFI
    exports and 55 Lua C globals. Simulation (MD, AI, jobs) calling the same functions passes untouched. Fail closed: pins of every
    entry on the pinned build or the session does not start; a lost patch stops with 164.
  - native_gate_ui_replay family 'events' (P3, first step): slot 1's AddUITriggeredEvent and SignalObject are captured and run on
    every client at the same tick through the stock functions; slots 2+ refused. That includes accepting/declining a mission offer
    (SignalObject 'accept'/'decline' to the offer's actor), slot 1 only.
  The worst case with the guard on is "that menu action does nothing yet", never a split, within the limits of section 3.

1. THE GUARD (lockstep_ui_guard.h, lockstep_ui_guard_lua.h, lockstep_ui_guard_table.h generated)
1a Inventory [F names, our classification]: tools/dev/ui_guard_inventory.py, from the functions the base game's menus call
  (gamelua/08/ui: 1949 FFI names in use, 665 not queries by name, plus the engine's Lua C globals used there). Kept: what changes
  the world or reaches MD. Left local on purpose: widgets, map display and filters, options (the stock settings fingerprint
  already covers the game options), cameras, read flags, logbook, player alerts, construction-map editing before its confirm,
  custom game starts, guidance (native_gate_guidance_local: the client's own), online services, statistics.
  Groups (count FFI/Lua): flight 50/8 (P0 left-overs: flight assist, turrets, drones, deployables, cover, seat, F-key PerformAction,
  target monitor RaisePlayerInteractionEvent, and the P0 entries of the replay families), orders 23/4, fleet 26, trade 27/15,
  faction 20 (player faction rules and identity), assets 22/12, build 10, conflict 16/1 (boarding, research, terraforming,
  diplomacy), missions 5 (AbortMission, SetActiveMission, SignalObjectWithNPCSeed*, MissionBriefingInteractButtonClicked), events 2
  (AddUITriggeredEvent, SignalObject), conversation 8 (StartConversationFromMenu, StartSubConversationFromMenu, ProceedFromMenu,
  ReturnFromMenu, CancelConversation, UnsuspendConversation, SelectDialogOption, SelectBackOption), session 3/2 (NewGame,
  NewMultiplayerGame, ConnectToMultiplayerGame, LoadGame: a client that loads leaves the shared world), cheat 4/3, editor 19.
  34 entries are "covered": a replay family hooks them or what they end in (travel 0x9fd120/0x9fd330 below StartPlayerActivity,
  the target sites below SetSofttarget and the radar clicks, the autopilot core, the dock and weapon hooks, the order hooks and the
  Lua order wrappers). While such a family is armed the guard leaves the entry alone (17 of them are the very RVAs the replay
  patches; the C test checks covered includes the hook's family for each). With the Play42P families 246 entries are installed.
1b Table [F]: tools/dev/gen_ui_guard_table.py resolves each name on the pinned X4.exe (PE export, or the Lua C function the engine
  registers under that global from x4-re's labels), decodes the entry with capstone and takes the shortest prefix of five or more
  bytes: no branch except one conditional branch (3 entries), no call or return, RIP-relative displacements moved at install
  (13 entries), nothing in the function jumps into it, inside one aligned 16-byte block (one CAS), no base relocation. Return
  kinds from the stock ffi.cdef prototypes: zero for void/bool/integers/IDs/float, an empty string for const char* (3), a zeroed
  struct with empty strings through the hidden pointer for UIFormationInfo and UICrewExchangeResult; the check-only argument by its
  parameter name (15 entries: a call with it set is a query and passes). Pin: SHA-256 of up to 512 bytes from the entry (the
  unwind range, no relocation). --check regenerates and compares (run by tests/test_native_gate_ui_guard.py when x4-re is at hand).
1c When it refuses: uirep_local_phase() (UI thread and one of: UI slot 6 depth, render slot 10, the slot 4 dispatch of presentation
  ids, an open presentation scope), and not uirep_replaying (an apply), not rid_probe_frame (the probe's own frame; the scripted
  triggers clear it around each op like a person's click), not after the window, a check-only flag not set. Everything else passes:
  other threads, the simulation phases, MD/AI calling the same exports or Lua functions.
1d Hook [F own code]: a 5-byte jmp at the entry to a per-entry stub (mov r10d,index; jmp shared). The shared routine saves rcx, rdx,
  r8, r9, r10 and xmm0..3, calls uiguard_decide(index, saved block) with rsp 16-aligned, restores everything and either jumps to the
  entry's trampoline (the moved prefix, its jump back, the branch's absolute target) or returns the refusal value in rax and xmm0
  (rax = the hidden pointer for a struct). Nothing of ours stays on the stack while X4's function runs. Region near the image
  (rel32 reach to every entry checked; a displacement that does not reach fails the install). Installed with the replay at its
  first pass, intact checked every pass (ui_guard_hook_lost, stop 164), removed behind the window (ui_guard_restore), restored on a
  gate stop. Arming: gate.ui_guard(groups) after gate.ui_replay, before the first tick; pins of every entry first
  (pins_ui_guard:<rva> refuses the arming and the probe asserts: fail closed on a build mismatch).
1e Seen and counted: UI_GUARD_PINS ok=1, UI_GUARD_ARMED slot= groups= entries=; every refusal one row
  UI_GUARD_REFUSED tick=<t> op=<name> group=<group> (64-row ring per frame, lost= counts overflow, the counters never lose);
  UI_GUARD_STATUS (every 120 ticks) ui_guard=live why= groups= entries=280 installed=<n> passed= queries= refused=<n> lost=
  by=<name>:<count>,... (most refused first); UI_GUARD_STOP at the end. The person sees X4's info line (ShowInfoLine 0x1ba8c0, at most
  every 90 ticks): "Multiplayer: <name> is not shared between the players yet - nothing happened." (our text).
  ShowInfoLine [F]: builds a string and calls a virtual (+0x2a8) of the GameClient's subsystem at +0x3b8; [I] pure presentation (it
  touches no simulation object directly; the callee was not followed). It runs in the probe's frame, which the guard passes.

2. THE EVENTS FAMILY (P3 first step; lockstep_ui_replay.h op 0x47, native_gate_ui_replay_core.lua)
  native_gate_ui_replay lists 'events' (bit 256; true does not include it). The Lua core wraps AddUITriggeredEvent and SignalObject
  by name: on slot 1's client a call in a local phase (gate.ui_replay_local: capture now and not the probe's frame) is encoded with
  the existing codec (strings, numbers, tables, components as runtime ID + portable check) and pushed as a Lua-run event; at
  capture tick + delay every client's probe frame calls the stock function with the same arguments, in slot order, the receipt
  (PUIREP_1 results) joining the pilot receipt. Slots 2+: refused (UI_REPLAY_REFUSED what=<name> why=slot), nothing runs; a section
  of slot 2+ carrying op 0x47 is refused natively (ui_events, stop 164). The probe's own AddUITriggeredEvent (fleet owner, MinHull,
  respawn) and the simulation's pass to the stock function at once. A value that does not encode (a non-component 64-bit ID such
  as a message ID) is refused (why=unmapped), consistently nowhere. The guard keeps its native hook on both as a backstop for a
  cached reference.

3. WHAT THE GUARD CANNOT DO (honest limits)
  - Only the inventory. A world-changing entry classified "local" by mistake, or one only a DLC or a mod's menu calls (the
    extracted UI is the base catalog 08), still runs on one client. The inventory is a reviewed list, not a proof.
  - Only exports and registered Lua C globals. Engine UI code that changes the world without them is not seen: keys go through
    the stock record (refused or replayed by the pstk verdicts as before); Anark widget callbacks into engine internals other than
    the target writer are not inventoried [I: none found that is not an export].
  - Symmetric automatic UI: an MD-started flow whose menu answers automatically on every client (e.g. a conversation menu that MD
    opens on all clients) is refused on every client alike: no split, but that MD flow may wait forever. Slot 1's events replay keeps
    AddUITriggeredEvent/SignalObject of such flows working (slot 1's client runs the handler too, once for everyone).
  - Not guarded on purpose: guidance and the active mission's guidance (SetGuidance/EndGuidance, section 14 of the replay report),
    Pause/Unpause, SaveGame, QuitGame, options, statistics (IncStatValue/SetStatValue), logbook, read flags, player alerts, online
    ventures. A difference there is the client's own data, not simulation state [I for statistics: MD could read them; none seen].
  - lockstep_player.h / lockstep_player_fire.h call SetSofttarget themselves (player command mode, not in the people config):
    with the guard and without the target family such a call in a local phase would be refused.
  - Live unknowns: ShowInfoLine visible in flight [I]; the call rate of guarded functions some menus call on open (UpdateProduction,
    TriggerCompSlotAnimation, AddKnownItem, AddUITriggeredEvent) only fills the log; a stock Lua menu that errors on a refusal value
    (the values were chosen from the call sites read, not from every caller) shows a Lua error in the debug log, nothing else.

4. P3: CONVERSATIONS, MISSION OFFERS, UI EVENTS
4a How a conversation flows [F scripts and binary]
  - Start from a menu: Helper.closeMenuForNewConversation -> StartConversationFromMenu(conversation, actor, convparam) (0x276980), or
    ProceedFromMenu (0x2765e0) when the menu itself belongs to a conversation; sub-conversations StartSubConversationFromMenu (0x276df0);
    a conversation menu's section choice ProceedFromMenu(nextsection, choiceparam); return ReturnFromMenu (0x277130); close
    CancelConversation (0x2772b0); UnsuspendConversation (0xb131c0) after a suspended menu. The interact menu's Talk/Comm uses the first.
  - Choices in the dialog: dialogmenu.lua leaveDialogMenu -> SelectDialogOption(button) (0xb145e0). [F] It reads one integer, takes
    the singleton at 0x38ee230 (one per process), walks its current option list (+0x80 -> +0x60..+0x68, entries of 0x90 bytes, button
    at +0x40), on a match clears +0x1a6/+0x1a9 and calls 0x11798f0(+0x110) and 0x11789d0(manager). 0x11789d0 [F]: only with a
    current conversation (+0x80) and state +0x1a0 in {4,5}; posts an event object through 0x99a720 at the thread block's time
    (+0x300) and hands +0x130/+0x158/+0x160 to the conversation (0x11764a0 or 0x11762e0). [I] That is the chosen section and its
    choice parameter arriving in MD as event_conversation_next_section (md/conversations.xml, genericmissions.xml, gm_*.xml,
    diplomacy.xml listen for it [F]).
  - DialogMenuShown/DialogMenuHidden (0xb150a0/0xb15060) [F]: a UI flag (0x38f4bfb) and input contexts, presentation only.
  - What MD reads: the conversation cues address player.entity / the actor; player.entity is slot 1's player on every client [F,
    replay report 3a]. The manager is one per client [F: a global], so a client holds one conversation at a time [I].
4b Mission offers and missions [F]
  - Accept/decline: menu_missionbriefing and menu_map call SignalObject(offer actor, 'accept'|'decline', offer as Lua ID); the
    gm_*.xml cues listen with event_object_signalled object="$Client" param="'accept'" [F]. So acceptance is a SignalObject: the
    events family carries it for slot 1. [I] Whether the offer's ID resolves in the component map (else why=unmapped, refused
    everywhere) is a live question.
  - AbortMission(id) 0x175860 and SetActiveMission(id|0) 0x1b7010 act on the mission manager 0x6cf1658: its mission list +0x60..+0x68,
    entries of 0x5d0 bytes, id at +0; SetActiveMission(0) tail-calls 0x113b920(manager,0,0,1), SetActiveMission(id) 0x113b760(manager,
    entry). One manager per world on every client, its active mission is the client's own guidance [F replay report 10]. Both guarded.
  - SignalObjectWithNPCSeed / ...AndMissionID (hiring, crew delivery missions) and MissionBriefingInteractButtonClicked: guarded.
4c AddUITriggeredEvent (0xb1c7c0, UI::XAnark::CoreLuaBindings) [F]: the menus' (screen, control, value) for MD's event_ui_triggered;
  tutorials (scenario_tutorials.xml alone has 224 listeners), diplomacy, rml_buildstation listen. The probe's own fixtures use the same
  route from its frame on every client at the same tick, which passed live (U5b, U7, U6c): the events family reuses that.
4d Slots 2+ [I]: MD has no player for slot k: player.entity, player.computer and the conversation manager are slot 1's / the
  client's single one. Re-raising slot k's event on every client would run slot 1's MD. Options, none built:
  (1) MD in slot scope: run the cue's actions with the singleton = P_k (pslot_enter) when the event came from slot k. Needs MD's
  player.* lookups to go through the singleton (unverified: MD may cache player.entity), and a per-slot conversation manager.
  (2) Slot k's conversations as slot 1's MD with an actor/target parameter for k, in our own MD (a coop layer): own scripts, not the
  stock ones. (3) Keep refusing (today).
4e What remains, in order of value
  - Conversations for slot 1 (StartConversationFromMenu, SelectDialogOption, ProceedFromMenu, ReturnFromMenu, CancelConversation as
    Lua-run events, the same mechanism as 'events'). Risk to settle first: the non-capturing clients show slot 1's conversation
    (MD opens it everywhere [I]); their manager must be in state 4/5 at the apply tick for the choice to take, and their own dialog
    stays on screen until MD moves on. Needs a live look at +0x1a0 on both clients (a gate row) before it is armed.
  - AbortMission for slot 1 as a generic native call (the mission ID as a 64-bit value, not a component reference).
  - The economy menus (trade, construction, crew): each is a world change with its own read-back (prices, queues); per family like
    the queue editor. Not started.
  - Slots 2+ for anything that reaches MD: 4d.
