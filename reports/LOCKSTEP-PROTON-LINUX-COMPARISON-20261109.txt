Coverage and interpretation
---------------------------
The captures contain 519363 objects at tick 1 and 519540 at tick 60. Motion
coverage remains unknown for 32611 and 32643 objects respectively, equally
on both peers. Equal captured roots therefore do not prove all engine state
is covered. Native input capture/replay, full player controls, a dedicated
server deployment, and remote Windows networking are outside this acceptance.

Source inspection identifies an actionable parity gap: Windows has a separate
fixture navigation RNG scope, NAV_UPDT, while the Linux cadence wrapper lacks
that scope. The current test did not enable native_gate_nav_rng. The existing
Linux nav_key uses a different domain and key tuple and is not a substitute.
The subsequent fixture-scope implementation and native result are below.

Fixture navigation follow-up
----------------------------
The Linux cadence hook now offers an opt-in fixture navigation RNG scope.
It uses the exact Windows NAV_UPDT tuple: tick, fixture actor number, zero,
one-based per-actor call ordinal, zero. It restores the incoming thread RNG
after each call, including nested scopes. Identity checks require the bound
owner, runtime identity and reverse controller pointer. Invalid time or RNG
increments the navigation failure counter; as on Windows, the original call
still executes and the next gate check stops. Nonfixture scopes are unchanged.

The Lua probe routes native_gate_nav_rng to the explicit Linux API rather
than pretending the Windows boot bit is implemented. Other unsupported boot
bits still refuse. The builder accepts this option only with the twelve-actor
snapshot fixture, serial pathing and world identities. Linux nav_key and this
fixture scope are mutually exclusive; no default is enabled.

primary review also ran 52 focused Python/Lua tests with no skips, rebuilt

Mass calculation investigation
------------------------------
The Windows creation-time body1 fallback is now implemented as an explicit,
default-off option. It applies the same policy as the existing Linux option:
only the second, fixed-mass physics body of the identified defined-mass shape
receives the sphere fallback. Body0 keeps its calculated inertia. This is an
experimental parity policy; it changes physics values, not digest coverage.

Independent synthetic tests under Proton found an unwind defect in the first
Windows trampoline. RtlVirtualUnwind interpreted its RIP-indirect continuation
jump as an epilogue. The revised trampoline uses the volatile R11 register and
passes the retained unwind cases. No X4 process was started by these tests.
The original failure and a direct comparison of both jump forms are retained.

The tests also exercise arm/STOP ordering, partial writes, failed protection
or cache restoration, and unresolved suspended-thread handles. Failed resume
and close operations retain their obligations for retry. A live thread that
cannot be resumed prevents a clean-restoration claim. Bounded lock acquisition
avoids waiting indefinitely for a suspended lock owner. The final focused
test executable, SHA-256
  49cdb6b1c320dc02da8d16ae74322869079608184cf0c8af72d02eb215be9e75,
passed under Proton with no remaining owned processes. That evidence precedes
the formatting-only follow-up and does not establish live mass parity.

Two existing FPENV activation limitations remain outside this correction:
failed hook installation does not roll back worker MXCSR values already
changed, and exceeding the thread-record capacity can leave changed threads
without a saved previous value. Do not interpret the focused lifecycle tests
as proof that every independent gate feature has complete rollback.

For body0, a copied-image experiment executes the pinned Linux and Windows
mass routines on identical inputs without running either game entry point.
The first localized difference is the association of the Jacobi theta
calculation: Windows computes (0.5 / a) * h, Linux computes (0.5 * h) / a.
For one identical operand pair this produces adjacent float values.

Changing only that instruction order in the private Windows image removes
all quaternion and physical inverse-inertia-lane differences in the retained
1,001-case corpus. Full motion-property byte differences drop from 301 to 3.
The three residual cases differ only in the fourth inverse-inertia SIMD lane;
they remain reported. Its relevance to all downstream consumers has not been
established. Linux outputs are unchanged. The primary audit independently
checked all 62 artifact hashes and parsed the raw before/after records.

The freeze helper now distinguishes a permanently terminated thread from a
live or unknown thread. After a failed suspension, only WAIT_OBJECT_0 on the
same thread handle allows enumeration to continue. The cursor remains open
until enumeration advances; close failures still retain cleanup obligations.
WAIT_TIMEOUT and WAIT_FAILED still refuse. This is not a blanket exception
for access-denied errors or for Wine threads. Upstream Proton's Wine source
also returns access denied for non-running threads, while a signaled thread
object means termination:
  https://github.com/ValveSoftware/wine/blob/proton_10.0/server/thread.c
That branch source is explanatory evidence, not an identity check of the
installed Wine binary.

Harness and validation
----------------------
tools/dev/proton_gate_live.py creates a fresh private prefix, game view,
profile and overlay beneath .local. Its bubblewrap namespace makes the host
filesystem read-only except for the owned run. It verifies the Windows image,
overlay manifest and snapshot, uses a common relay and absolute arm time, and
requires the expected STOP slot/tick/reason/restoration. Cleanup authenticates
owned processes by UID, start identity and exact prefix; it never restarts
Steam. Local clean STOP does not imply agreement with the other peer.

tools/dev/linux_gate_live.py supports a specified external relay and common
arm time. Its local-only result must be combined with the other peer and
relay evidence. Original games, normal profiles and Workshop files are not
written by these runs. Retained receipts report no owned survivors.

Windows synthetic gate and wire-crypto tests also pass under Proton. The
gate test additionally reads and verifies the pinned PE image; that unit
test does not launch X4. One negative test formerly assumed address 0x10000
was unreadable, which Wine disproved. It now allocates an owned PAGE_NOACCESS
page and tests refusal against that page. This changes the test fixture only.
Evidence: prefix-smoke-2/windows-tests-native-image-result.json and
windows-tests/before-fixture-readability/receipt.json.
