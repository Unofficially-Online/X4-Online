LOCKSTEP SUIT VIEW: WHY CENSUS MISSILE1 PARTED AT TICK 1733, AND THE FIX
1 November 2026 | offline work on branch contrib/ferrite-suitview (base: smoke 633a1bc7). Evidence: the coordinator's run
census/missile1 (build149 = smoke 621defba, overlay-Missile1: the combat people config, factions hostile, slot 1 = the player's
scout ae79c, slot 2 = Argon Elite a5374 with missiles, aim + scripted fire + scripted missiles, victim-decided hits, death + suit
for slots 2+ + respawn 300), read with bounded greps of exact tags and tick ranges in the two engine-output.log files. Static
analysis of the pinned Windows X4.exe 9.00 (RVAs, base 0x140000000) in x4-re; nothing of it is copied here. No X4 was launched.
[F] = read in the logs or the binary; [I] = inference.

0. QUESTION AND ANSWER
  Asked: once slot 2 sits in its spacesuit, client 2 (which presents slot 2) evaluates one view point more than client 1 (VIEW_POINTS
  at 1740: calls/evaluations 20 against 21, level 9 0 against 1); why, and make every client derive the same view points.
  Answer: the view points are not where it starts, and they are already the same on both clients. The first difference is slot 1's
  soft target, at the death tick itself (1733), written on client 1 alone by X4's UI target manager when its target element died
  with slot 2's ship. MD's Player_Changed_Target then took one more shared runtime ID on client 1, and every later ID, tempzone and
  count parted from there; the extra evaluation at 1740 is one of those consequences, not the cause.
  Fix (lockstep_ui_replay.h, inside the existing default-off target family of native_gate_ui_replay): outside the local phases a
  soft target write is the simulation's only when MD's set_player_target / clear_player_target is on the stack; anything else is
  the UI's own and becomes this client's slot event, replayed on every client at the same tick, as a click is.

2. HOW X4 GOT THERE [F binary, I order]
  The soft target writer 0xaecb60 (UI code with the simulation half inlined in two blocks, both patched by the target family) is
  reached from: UI::CUIController vfunc 72 0xb3f7c0 -> 0xaeb150 (FFI SetSofttarget, the HUD's target system, MD's
  set_player_target), the per-frame update in CUIController::Move (slot 6), the target system reset 0xae8d80 (CUIController event
  slots 13/66/97), MD's clear_player_target (0xae8080 -> 0xaebef0 -> 0xae8460), and the UI target element's disconnect 0xaeb970,
  which its destructor 0xaeb4e0 calls (UI::ICom::GenericPOSSink::vfunc4 0xad7050 -> 0xad7440 -> tail jump 0xaeb4e0). An element
  dies with its component; slot 2's ship died in the simulation, outside every local phase. Client 1's target manager held 1522e as
  the soft target (its UI is slot 1's), so the disconnect cleared it and the manager chose the next one: both blocks, stock, on
  slot 1's player. Client 2's UI presents slot 2 and targets for slot 2, so its element of 1522e was nobody's target: nothing ran.
  The replay's design note (LOCKSTEP-UI-REPLAY-20261030 section 3 and its "not live" list) assumed that MD is the only caller
  outside the local phases (target_passed expected 0); missile1 is the first run where a slot's target died, and it is not.
  The 1741 change on client 2 fits client 1's targetsystem.lua following up in slot 6 (captured, delay 3) [I]: on client 1 that
  replay set the same target again (Player_Changed_Target 2 -> 3), on client 2 it was the first change (1 -> 2).
  MD's routes, the only simulation callers [F]: MD::SetPlayerTargetAction::vfunc3 0x1135bc0 (vtable 0x2c74740 slot 3) calls
  CUIController vfunc 72 at 0x1135ea0 (return 0x1135ea6); MD::ClearPlayerTargetAction::vfunc3 0x1135f20 (vtable 0x2c747b8 slot 3)
  calls 0xae8080 at 0x1135f36 (return 0x1135f3b). In the base game scripts only scenario_tutorials.xml uses set_player_target and
  nothing uses clear_player_target.

3. THE FIX (lockstep_ui_replay.h; part of the target family, so default off with native_gate_ui_replay)
  uirep_target_route decides each block call:
    a local phase (as before)            capture as this client's slot event;
    the replay applying, or past the window (as before)   stock at once;
    MD on the stack                      stock at once (the simulation's own, every client at the same tick; target_md=);
    anything else, frame thread          capture as this client's slot event (target_ui=, the route in target_route=);
    anything else, another thread        refused: nothing runs anywhere (target_ui=../<refused>).
  "MD on the stack" = 0x1135ea6 or 0x1135f3b among the image return addresses above 0xaecb60. The walk unwinds by the tables: its
  own frames and the stub up to the stride (on the replay's page, no table), which runs in 0xaecb60's own frame and moves no stack
  before its call, then 0xaecb60 from the block's resume (0xaed0b3 / 0xaed219: inside its .pdata range, not an epilogue) and its
  callers by X4's .pdata, at most 12 image frames, under SEH. Anything it cannot unwind is "not MD": the write is captured or
  refused, never applied on one client. Pins added: both MD functions (SHA-256, the call bytes inside them) and their vtable slots.
  What the capture means: the client's own UI reacting to its own presentation (its target died, the next is chosen) becomes the
  presented slot's event, applied on every client at capture + delay through 0x3e7560 / 0x3e73f0, exactly as a click. A target
  already gone at the apply is stale on every client alike. Slot k's UI reacting outside the scope now writes slot k's player (via
  the replay) instead of slot 1's on that client alone.
  Status (UI_REPLAY_STATUS, with the target family): target_ui=<captured>/<refused> target_md=<n> target_route=<up to 6 image
  return RVAs of the last UI route, "-" before one> route_faults=<walks ended by a fault>. target_passed= keeps counting the stock
  calls (MD, the replay, past the window). Cost: one table walk per write outside the local phases (two in all of missile1).

6. LIMITS
  - Not live: the walk on the real stack and the recorded route are inference until the rerun (the image test covers X4's tables
    with synthetic stacks, not a live frame).
  - Semantics, deterministic but new: a UI reaction outside a local phase is the presented slot's event. A reset of the target
    system on client k triggered by another slot's world change (if X4 does that outside slot 6) clears slot k's target on every
    client, where before it wrote slot 1's on client k only.
  - An MD action other than the two above that reaches 0xaecb60 would be captured as the presenting client's event; none is known.
  - The 9fcd70 / 9fccd0 lazy clear of a dead target ID stays local (the receipt already shows a dead target as 0); all readers
    resolve the ID, so 0 and a dead ID read the same.
  - The suit is still no viewpoint (deterministic: the same on every client). Simulation around a slot in its suit runs at the
    attention slot 1's ship gives it; a viewpoint for a seated suit would be a separate, default-off change.
