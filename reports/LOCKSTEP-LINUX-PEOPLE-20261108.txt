LOCKSTEP LINUX PEOPLE STACK (the players' modules on the Linux gate)
Started 8 November 2026 after the cancelled playtest (no Linux client). Split with x4mods-e7: the simulation keys and
the defaults mechanism are e7's (reports/LOCKSTEP-LINUX-CATCHUP-20261104.txt, "A LINUX PLAYER IN A WINDOWS SESSION");
the people stack is this report's: player_identity, pilot_slots .. pilot_death_suit, hit_claims, ui_replay, ui_guard,
pilot_foot and its bodies/slots, player_settings_per_slot, guidance_local, render_fps/camera/motion, own_predict.

1. SIZE
  The Windows people stack (src/native/engine/lockstep_pilot_*.h, lockstep_ui_replay*.h, lockstep_ui_guard*.h,
  lockstep_render_*.h, lockstep_own_predict.h) pins about 600 distinct X4.exe addresses: functions, call sites, data
  words, vtables. Largest: ui_replay 88, pilot_native 101, pilot_slots 45, pilot_foot 41, pilot_fire 35, pilot_stock
  30, pilot_present 26, pilot_inputs 22, render_display 20, and the UI guard's table (288 exports by name: the same
  names exist on Linux).
  The Linux X4 (ELF, GCC 14.2) keeps no names for X4's own code: of 28644 defined dynamic symbols none is in
  namespace U. Named on both: the 2378/11360 plain C exports (the Lua FFI API; 2024 same names) and RTTI class names.

2. TOOLS (offline, read both binaries; tests/test_linux_pair_tools.py)
  tools/dev/linux_pair_rtti.py   vtables by RTTI class name and offset: 2958 classes, 3542 vtables. Linux slot =
                                 Windows slot + 1 after the destructor (GCC's two): 14 of the 19 known function pairs
                                 that sit in paired vtables are exactly one slot later (the 5 others are MSVC-folded
                                 stubs); 3182 of 3542 Linux vtables have exactly one slot more.
  tools/dev/linux_pair_calls.py  function ranges (.pdata; .eh_frame_hdr and the FDEs), a capstone sweep (calls, string
                                 references, references to writable globals), anchors (known pairs, same-name exports,
                                 unique vtable slots, strings one function references on each side), then votes: a
                                 one-call gap between aligned calls pairs only when two paired parents agree; identical
                                 paired-callee or paired-global signatures. 9965 pairs.
                                 Held out against tools/dev/lockstep_linux_known_pairs.json: 19 of 68 found, 19 right,
                                 0 wrong. (Single-parent gaps were wrong 3 of 3: MSVC and GCC inline differently.)
  tools/dev/linux_pair_candidates.py  leads for one unpaired function: votes from paired callers and callees, sizes,
                                 and the share of struct field offsets ([reg + 0x..]) the two bodies use.
  tools/dev/linux_people_sites.json  the people stack's Windows sites with their Linux counterparts and evidence.

3. PILOT CORE (lockstep_pilot_inputs.h), 12 functions: 7 placed
  9fc550 controller getter -> 1dd19d0 (3 paired parents); d8e5b0 input value by index -> 1663740 (2 paired callers,
  size 4712/4464, 30 of 112 field offsets shared); d9cc30 controls refresh -> 165d860 (2 parents); b09880
  IsFlightAssistActive, 179760/175a00 De/ActivatePlayerControls (exports); ced70 find (known).
  Open: ea7600 boost, ea7650 travel, d8dd50 authority, d8d9d0, 1252850. The first three are 64..96-byte predicates
  over the controller's entity (+0x28): travel = component(entity) +0x340 != 0, boost = 54ce90(component, time),
  authority = two globals, virtual slot 49, a global byte and entity +0xd1. In the one paired caller (d95180 ->
  166d020) GCC leaves no separate call for them: most likely inlined. The Linux gate can then reimplement them from
  their fields, once the component getter 6d6d80 (entity +0xa8 list walk) and 54ce90 are placed and the offsets
  checked on Linux.

3b. THE COMPONENT GETTER 6d6d80 (called by 62 Windows functions; the three predicates' first step)
  Not a plain getter: a typed lookup. entity +0xa8 is a component container (count +0x20, a vector of 32-byte buckets
  at +0x8/+0x10, the walk starts at bucket 2); each candidate passes a class-mask byte (global 0x6cf3250 against the
  component's class index +0x68) and a static predicate object, U::ComponentFilterByClass at 0x31bc5f0 (its vtable
  call +0x18); the first match is written to the out parameter. On Linux the same shape (rdi +0xa8, then +0x20) starts
  three functions: 147f900 (352 bytes) and 14e8760 (368) read a mask byte (0x3daae50), 14bbb00 (272) calls a filter
  object (0x3ed1840, vtable +0x18): instances of one template for different component classes, GCC splitting what
  MSVC keeps in one body. Which is the travel/boost component's: the class id each filter object gets in its static
  initializer (Windows: the writer of 0x31bc5f0's fields; Linux: of 0x3ed1840's), next.
  Resolved by a reading: 6d6d80 -> 147f900 (the same walk from bucket 2, the mask byte, the out parameter); 14e8760
  starts at bucket 4 (another category), 14bbb00 is a bool "has a component of class 0x54" test.
  54ce90 (boost: component +0x2e0 double, 4bb560 duration): no Linux function of up to 200 bytes reads +0x2e0 as a
  double and calls: inlined into its callers or at another offset; next through 147f900's Linux callers.
  The offsets agree where seen so far (+0xa8, +0x20, 32-byte buckets): a sign that the component layout is shared.

3c. INLINING: THE LINUX GATE REIMPLEMENTS SMALL HELPERS
  147f900 (the getter) has one Linux caller (cc5ec0, 101104 bytes) against 62 Windows callers: GCC inlined the lookup
  nearly everywhere, and with it the 64..96-byte predicates (boost ea7600, travel ea7650, authority d8dd50). No Lua
  export reports boost or travel state (both builds export CanStartTravelMode, GetBoostEnergyPercentage, IsSetaActive,
  IsFlightAssistActive, IsAutoPilotActive, IsPlayerControllingShip, GetPlayerControlledShipID). So the Linux pilot
  capture reimplements them from fields, as the Windows gate already does for other engine logic: the bucket walk
  (+0xa8, count +0x20, 32-byte buckets from 2, the class mask byte, the filter object), travel +0x340, boost +0x2e0
  with the duration from 4bb560. Each field offset is confirmed on Linux by a reading of an inlined site before use
  (cc5ec0 holds the getter's only out-of-line call; the inlined copies are found by the +0xa8 walk from bucket 2).

  174 distinct sites (tools/dev/linux_people/coverage.py, code constants of 0x40000 and more in an X4.exe section).
  Placed 64 (tools/dev/linux_people_sites.json): inputs 15/23, native 29/79, stock 4/16, slots 5/26, present 8/15,
  stock_view 0/10, camera 2/4, eye 1/1. Methods and their held-out precision:
    - functions: anchors + votes (19/19), neighbour extension (linux_pair_neighbors.py: a pair's next/previous
      functions, sizes within 2x, 30% of field offsets shared; +299 pairs, 0 wrong held out), batch candidates
      (2+ votes, 25% fields, sizes within 2x, no close rival: 6, among them 1252850 -> 104f220, 717ed0 -> 1379aa0);
    - globals: aligned votes (5/5), blocks (4/4; the input bank 2f4b720..828 at +0xE42280);

  The automatic passes plateau here: most open sites are functions of the input module with no paired neighbour

  the Linux machine (which functions run when a control id is dispatched, a menu opens, the map opens), which would
  place the dispatchers and SPACE handlers directly.

3e. CONTROL IDS ARE THE SAME ON BOTH BUILDS; THE HANDLER REGISTRATION IS NOT
  The stock record carries X4 control ids (kind, id, value). Both builds have the same 447 input names
  (INPUT_STATE/ACTION/RANGE_*), and their name tables ({name pointer, value} pairs of 16 bytes: Windows one copy per
  translation unit, e.g. 0x2468200 (408 states and actions) and 0x246a960 (39 ranges); Linux one, 0x3b263c0 and
  0x3b26140) give every name the same value: 447 of 447. A Windows player's stock record means the same on Linux,
  so the wire needs no translation.
  The registration differs: Windows 71b6c0 registers handler 71bac0 for ids 0xa9 (NEXT_TARGET_ACTION), 0xaa, 0xd5,
  ... with one call each (0x1255610(table +0x63e0, id, handler)); on Linux no function loads that id sequence, no
  data array holds it (u16/u32/strides 8..48), and the ids appear together only as the cases of 1393520 (10272 bytes,
  163 calls: case 0xa9 calls 1c91aa0(0xa9)): the handler's switch, perhaps 71bac0 with its callees inlined (71bac0 is
  2944 bytes, 70 calls; 8 of 73 field offsets shared: not conclusive). The other stock handlers are a 1072-byte
  function (d86c80) and two thunks of 31 and 33 bytes (d870b0, d87f70).

  shift+1 10 (s, e, d: 0, the first key of each axis took them). 17 entries inside pinned gate ranges were left

  Matching the open Windows functions against the 328 input-only functions by field offsets and size
  (tools/dev/linux_people/cov_match.py) gives 11 clear leaders, but none has call-graph support (0 votes each) and

3g. THE WINDOWS TRACE (8 November evening): BLOCKED BY THE GATE'S OWN CODE CHECKS
  Built: build_native_gate_overlay/build_play_overlay --coverage for the Windows gate, native_gate_map_test, the
  stock event script (tools/dev/linux_people/stock-events.lua), tools/dev/linux_pair_traces.py (event buckets on
  both sides, pairs by shared fields with a clear lead; tests in test_linux_pair_tools.py).
  Four lane runs (trace-w1 .. w4, defaults stack) stopped at tick 0..1: the coverage int3 of a listed function that
  has not run yet breaks every check that reads its bytes later. In turn: the world hash's nav layout pins (the table
  in lockstep_world_hash.h), the 8-byte prefixes it checks at 0xea4c00/0xe85360, nav_player's head of
  PlayerController::vfunc33 0xd97e80 (stop 95), the region camera's check (stop 165). Excluding everything the 42
  per-tick checks pin (tools/dev/linux_people/cov_exclude.py) keeps only 29 of the 57 open targets and still misses
  checks of other forms (165). So the Windows gate needs what the Linux gate got (b1688473), in its own form: code
  reads of the integrity checks overlay the original bytes under coverage marks (as tsnap_unpatched_hash does for the
  travel snapshot's byte), or coverage skips a registry of checked ranges. Until then the Windows trace waits.
