LOCKSTEP UI REPLAY: BUILDING AND ASSETS (FAMILIES 'build' AND 'assets')
1 November 2026 | offline work on branch contrib/ferrite-build (base: smoke a2e43713). Static reading of the pinned Windows X4.exe 9.00
(RVAs, base 0x140000000) and of the extracted stock UI scripts and ffi.cdef prototypes in x4-re; nothing of them is copied here (API
names, menu function names and RVAs only). No X4 was launched. [F] = read in the binary or the scripts; [I] = inference; "live" = what
only a native run can show. Builds on reports/LOCKSTEP-UI-REPLAY-20261030.txt (the replay) and LOCKSTEP-UI-GUARD-20261101.txt (the guard).

0. RESULT
  Two new replay families, default off: native_gate_ui_replay lists 'build' (bit 4096) and/or 'assets' (bit 8192); 'true' does not
  include them; both need native_gate_ui_guard. Bits 1024 and 2048 are left free for the trade and mission families.
  - build: ship purchase, upgrade and repair at shipyards, wharfs and equipment docks (the ship configuration's confirm: money, build
    task, transferred money, repair signal, as one batch), queueing (immediate or queued is AddBuildTask6's flag), plots (reserve,
    extend, pay, remove), the build storage, the construction budget (money to the build storage), the modules' loadout level.
  - assets: crew exchange, hiring/assigning actors and pilots, reassigning and firing crew, releasing from transfer, renaming
    (SetComponentName: ships, stations, the player's own name), claiming ships, selling ships, ship storage (put, take, request),
    equipment and paint mods (install, dismantle).
  Slots: every slot in coop mode; slot 1 only in factions mode; inventory mods slot 1 only (section 2). What a delayed apply cannot
  answer stays refused by the guard: the station plan editor's commit, a pilot made from a crew member (section 3).
  Worst case with the families on: an action happens a few ticks late, or (refused) not at all, on every client alike.

1. MECHANISM (src/native/engine/lockstep_ui_build.h, lockstep_ui_build_lua.h, tools/dev/native_gate_ui_build_core.lua)
1a Claims on the guard's hooks [own code]. The guard already hooks all 280 inventoried entries with a generic stub and shared routine
  (argument registers, xmm0..3 and the stack saved, then a decision, then X4's trampoline or a refusal value). The families claim 29
  of its FFI entries by name at their arming (gate.ui_build, after gate.ui_replay and gate.ui_guard, before the first tick):
  lockstep_ui_guard.h got two registration points: a claimed entry is installed whatever the guard's groups say, and in a local phase
  the claim answers first (after the guard's own pass rules: not the UI thread / not a local phase / the probe's own frame / an apply /
  past the window: X4's function runs; a check-only call is a query and runs). A claimed entry whose family is not armed falls back to
  the guard's rule. So no new code patch, no new pins for the entries (the guard's 280 pins hold), and one decision point for the
  guard and every family that wants to capture at its hooks (the trade and mission families can claim the same way).
1b The batch. Every claimed call one client's UI makes between two probe frames is one batch: a click handler runs inside one frame,
  so a menu's commit (several calls in one frame) is one batch. Lua C globals join the batch as Lua records through gate.ui_build_add
  (the Lua core encodes them with the replay's codec): SetComponentName always (assets); TransferPlayerMoneyTo, TransferMoneyToPlayer
  and SignalObject(.., 'repairs_initiate', ..) only inside a commit scope (1d). An event of any other family closes the open batch
  first (one line in uirep_push), so every event of a slot keeps the call order across families (e.g. the ship configuration's Repair
  order through the queue family, then the build task's batch). The batch leaves at the probe frame, at a scope's end, or when full.
1c Wire. A batch is version | record count | records; a record is kind ('N' a claimed call, 'L' a Lua record) | id | flags | length |
  payload. Arguments by a per-claim spec (h hidden struct pointer, I/i component, B plot binding, t build task token, u 64-bit, b byte,
  s/z string, f float in a register, F float on the stack, P UIPosRot*, C Coord3D*, L UILoadout2*, T CrewTransferInfo2*,
  X AddBuildTask6Container*, G GenericActor*, N NPCSeed* + count, R CrewTransferContainer* + count, k check-only). Structs are read
  through their stock layouts (mirrored in C with static asserts; the Lua core compares the menus' cdefs with ffi.sizeof/offsetof at
  the arming and refuses on a difference). Strings are kept once per batch (a ship's loadout repeats its macros). Components are runtime
  ID + 32-bit portable check (the replay's reference), or zero, or "the answer of record j of this batch".
  The batch travels as parts, op 0x50 (a Lua-run op: the replay's native section check accepts it with the families armed), up to 197
  bytes each, at most 48 parts (9456 bytes), all or none: a batch that does not fit the replay's queue is dropped before anything is
  queued (nothing ran anywhere; a row and the info line). One part per tick fits next to the stock record (section 236 bytes).
1d Commit scopes (Lua). The stock menu functions that pay and build in one click are wrapped once each menu exists (the handlers look
  them up when the menu is displayed): ShipConfigurationMenu.buttonConfirm and .buttonInstallMod, StationConfigurationMenu
  .buttonConfirmMoney, .buttonSetMoneyToEstimate and .buttonBuyPlot, MapMenu.buttonBuyPlot and .buttonSellShips. Inside one (a person's
  click: a local phase) the money globals and the repair signal are replaced by capturers for the call and restored after (also on
  an error), and the batch leaves at the end. Outside the scopes the money calls go to whatever else takes them (the trade family, else
  the guard refuses them). Every other SignalObject inside a scope goes on to the events family / the guard as before.
1e Apply (every client, the capturing one included and not earlier). Parts are staged and applied like every Lua-run event (capture
  tick + delay, slot order, call order); the replay core hands op 0x50 to the build core (registration: S.ops), which reassembles
  natively per slot (gate.ui_build_part) and, when the last part applies, steps the batch record by record in the probe's frame,
  canonical (no slot scope), with the replay's bypass on: a claimed call through the entry (the guard passes it, the trampoline runs
  X4's function), a Lua record through the stock Lua function. A whole batch is checked before its first record runs (version,
  records, every argument walked): a malformed batch stops (164, ui_build_batch/_record/_claim/_lua). A torn batch (a part missing or
  out of order: the same parts on every client) is dropped everywhere. A reference that resolves to nothing skips that record
  (skipped=gone, the same everywhere); a portable check that differs stops (164, ui_ref_mismatch); a fault in a replayed call stops
  (164, ui_fault).
1f Receipt. UIBUILD_1:<tick>:<batches completed this tick>:<hash over every batch's bytes and every record's answer> plus :M<player
  money> joins the replay's receipt (registration: S.extras), so a batch or an answer that differs, or a wallet that parts, is a digest
  mismatch at that tick. Rows: UI_BUILD_ARMED, UI_BUILD_SCOPES, UI_BUILD_APPLIED (each record, X4's answer), UI_BUILD_DROPPED,
  UI_BUILD_REFUSED (capture refusals of this client; the info line "Multiplayer: <name> is not shared for your slot yet - nothing
  happened." at most every 90 ticks), UI_BUILD_STATUS (every 120 ticks), UI_BUILD_SCRIPT, UI_BUILD_FUND.

3. WHAT STAYS REFUSED (the guard, as before) AND WHY
  - SetConstructionSequenceFromConstructionMap (station configuration buttonConfirm, the plan commit) [F 0x1dc030]: it resolves the
    container (0xced70), resolves the holomap ID through 0x1beb30 (a UI object of this client), takes the construction map's plan
    (holomap +0x2c0 -> +0x300), finds the container's builder context (0x3f76f0, then the +0x70 parents to class 0x6f) and builds the
    change through 0x3aa1d0 (0x390 bytes). The plan the person edited exists only in that client's holomap; there is no stock function
    that sets a sequence from data (the FFI has Save/Export/Import of library plans and ShowConstructionMap, all through a holomap).
    Design for the next step (not built): the commit is one record carrying the plan: GetBuildMapConstructionPlan2 (macro, offset,
    connection, predecessor, fixed, bookmark per module) and each module's loadout (GetConstructionMapItemLoadout2) - several kB, so
    parts as today - and every client rebuilds it either natively (an own ConstructionPlan builder for 0x3aa1d0, needs the plan's
    layout: RE) or through a library plan: ExportMapConstructionPlan writes the plan's XML on the capturing client, the bytes travel,
    every client's gate writes the same file under one name and ImportMapConstructionPlan + an MD cue with create_construction_sequence
    / apply_construction_sequence on the station applies it. Both need a live look first. Until then the editor's local editing stays
    local and the commit is refused with the info line (nothing happens anywhere).
  - CreateNPCFromPerson (player info "replace pilot" without an old pilot): the menu uses the new NPC entity at once (SetEntityToPost,
    SignalObject npc_state_reinit). A token like AddBuildTask6's would need SetEntityToPost (fleet group) and that SignalObject in the
    same batch: possible with this mechanism, not claimed yet. The map's pilot replacement through AssignHiredActor is replayed.
  - SetContainerBuildMethod (trade group): left to the trade family. Hiring a construction vessel (MapMenu.selectCV,
    InteractMenu.buttonDeployToStation: fee + deploy order) is not a scope: with native_gate_pilot_block_orders the deploy order is
    blocked, a fee without it would buy nothing; and without a committed plan there is nothing to build.
  - In factions mode slots 2+ (all of these): slot k's ships are x4lan_player<k>'s, the stock menus treat only `player` as the
    player's [I], money would leave the `player` account and a build would be `player`'s. Refused at capture (why=factions), skipped at
    the apply if a client sends one anyway (the same everywhere).
  - Inventory mods for slots 2+ (why=inventory): the apply is canonical, so X4 would take the mod from slot 1's player's inventory.
    Needs the apply in slot k's scope (the generic call path of the flight families does that natively in path_release) together with
    the Lua records in the probe's frame; the order between them is the open question.

4. MONEY, AND THE TRADE FAMILY (coordination)
  Rule (coordinator default): coop players share the player faction's wallet; in factions mode each player pays from its own faction's
  account. Here: in coop every slot's purchase moves money from the shared `player` account at the apply tick; in factions mode slots
  2+ are refused until a per-faction money op exists. Interface for the trade family (please keep or tell): (1) the build core captures
  TransferPlayerMoneyTo / TransferMoneyToPlayer only inside its commit scopes (1d) and only for the call (the globals are swapped and
  restored), so a trade wrapper installed before or after is never bypassed outside those scopes and never double-captures inside;
  (2) the records are Lua records 1 and 2 of a batch (K.LUA), applied through the stock function (or whatever X4LAN_UI_REPLAY_STOCK
  holds); (3) when the trade family has a money op that pays from slot k's faction account, the build core's records 1/2 for slot k
  should go through it and factions mode can open slots 2+; (4) SetBuildTaskTransferredMoney (a trade-group entry) is claimed here
  because it only follows AddBuildTask6 in the same click; (5) bits 1024/2048 and ops below 0x50 are not used here; the guard's claim
  hook (uiguard_claimed / uiguard_claim_fn) is a single function today: a second claiming family needs a dispatch by entry (trivial).
  The receipt's :M<money> catches a wallet that parts, whoever moved it.

6. RISKS
  - [I] Objects made by a replayed call in the probe's frame (ReserveBuildPlot's station; later the built ship) take runtime IDs on the
    route the probe frame's creations take; the queue family's orders (U7) passed live the same way, a plot station was not tried.
  - [I] AddBuildTask6 / ReserveBuildPlot / crew calls might read the player entity (the canonical one in the probe's frame) for
    something beyond the faction: then slot k's purchase would be slot 1's in that respect. In coop the faction is the same.
  - Stock struct layouts: checked against the menus' cdefs at the arming (sizes and every offset used); a menu not loaded yet is only
    reported (missing=), its first call then uses the mirrored layout.
  - Scope wrappers are installed when a menu table exists; a menu that is created later than the probe looks would have its first
    click before the wrapper: then its money call is the guard's refusal while its build call is captured (a purchase without payment).
    The stock menus exist at UI load [F: table.insert(Menus, menu) at file load]; the row UI_BUILD_SCOPES shows each wrap.
  - A batch dropped (queue full, too long) after the menu got its answers: the menu believes it happened; nothing happened anywhere.
  - A person changing the slot ship (claim, sell, storage of the occupied ship) is not guarded beyond what X4 checks.
  - The live paths are inference until run: AddBuildTask6 with a token-free answer on the capturing client's menu, the build queue on
    both clients, crew exchange answers equal on both.
