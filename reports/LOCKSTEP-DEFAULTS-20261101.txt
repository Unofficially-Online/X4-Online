LOCKSTEP SESSION DEFAULTS: EVERYTHING ON BY DEFAULT, FAIL LOUDLY NOT SILENTLY
1 November 2026 | branch contrib/ferrite-defaults (base: smoke e1f24256) | offline work: Lua/Python unit tests and the
gate build/test harness; no X4 was launched, no lane tool was run. The live test is section 9 (coordinator).

0. DECISION AND RESULT
  User (1 Nov): "everything should be on by default, fail loudly not silently". Coordinator's reading, implemented as is:
  (1) the mod stays inert without a lockstep session; (2) once a session is configured, every feature and sync fix that
  works is ON unless the session config sets that key to false; (3) diagnostics and measurement keys stay OFF (listed in
  section 3); (4) every refusal, unsupported combination, skipped default, unmapped/degraded counter, failed arm or stop is
  an ERROR row with the reason plus an in-game info line (X4's ShowInfoLine, the UI guard's path), and a stack that could
  split stops before the boot.
  Result: a session config with only native_gate_test, slot, port, token, native_gate_clients and the identity plan now
  arms the people stack of Play42P plus the newer features (render frames 1-3, own-ship prediction, UI guard, all 16 UI
  families, slot 1 on foot, per-slot player settings). Unit-tested end to end up to the boot: the probe accepts that stack,
  arms it on a mock gate and folds its digest into the boot data (tests/test_native_gate_defaults.py, ProbeTests).

1. MECHANISM
  tools/dev/native_gate_defaults.lua (the one source of truth) defines X4LAN_NATIVE_GATE_DEFAULTS:
  - D.ON: 172 entries {key, value, needs, why} in arming order (a key's prerequisites come before it). needs tokens: 'key'
    (on), 'key=value', 'key~item' (a list holding item), '!key' (a conflict), '@wire3' (native_gate_clients), '@plan' (the
    identity plan), '@fixed' (not protocol 5). Derived values: '@plan_ships' (pilot slots = the plan's slot ships),
    '@plan_stock' / '@plan_nodevice' (one 'stock' / false per plan slot), '@plan_window' ({max(40, setup tick + 16), 72000}),
    '@families' (every UI family whose prerequisites hold). '@credential' and '@configured' have no default (section 4).
  - D.apply(cfg): only when native_gate_test is set. A session needs slot pN, port and token (else a refusal). Explicit
    false or 'off' on a default key removes it (absent = off for every gate key) and is reported; a key the config sets is
    kept; every absent key gets its default when its needs hold, otherwise it is SKIPPED with the reason. Explicit
    combinations the relay or the gate refuses are errors (stop before the boot). Idempotent: the report stays in
    cfg._native_gate_defaults (the overlay loads the module first, the probe applies again and gets the same report).
  - native_gate_defaults = false: the bare gate (every key as configured, absent = off); logged as DEFAULTS_OFF.
  - D.stack: every default key's effective value (the wire crypto credential only as set/off, it is a per-slot secret).
    The probe folds SHA-256(stack) into the boot data ('|DEFAULTS_1|'): the relay compares the tick-0 digests, so a client
    running another stack stops at tick 0 instead of splitting later (row DEFAULTS_STACK digest=...).
  Load order: the overlay builders put ui/native_gate_defaults.lua FIRST in ui.xml.files (the identity and orders adapters
  read X4LAN_CONFIG while loading). The probe refuses to start without the module unless native_gate_defaults = false
  (ERROR DEFAULTS_MISSING + info line): a client without it would run another stack than its peers.
  Python mirror: tools/dev/native_gate_defaults.py parses the Lua file (strict one-entry-per-line format) and applies it
  the same way (tests compare both on several configs: applied keys, skipped keys and values are identical).
  - check_gate_options.py checks a session config on its effective config (defaults applied); errors of the defaults are
    failures; the CLI prints DEFAULTS and every DEFAULT_SKIPPED. An empty session config validates with no failure.
  - native_gate_players.py: on a session base the overlay writes only the lines that differ from the defaults, and an
    explicit false for every piloting/UI default its flags leave off (so the overlay runs what it validated); the final
    config is checked with check_gate_options (a failure refuses the build). New --defaults-only (--source stock): writes
    only the clients and the identity plan. The default stack's files are shipped (UI_FILES/MD_FILES in the mirror).
    Bases without port/token (the existing tests' fragments) are unchanged. `config` still prints the full block.
  - build_native_gate_overlay.py: a battle snapshot overlay on the Windows gate is a session with the default stack (its
    files shipped, the module first); --bare, the Linux gate (core subset), fixed-tick boots, clock mode and the two-player
    fixtures (command test, player probe, docking) write native_gate_defaults = false with the reason (printed).

4. CONFLICTS AND HOW THE DEFAULT STACK RESOLVES THEM
  - Protocol: default protocol 4, lookahead 1, pilot delay 3, with render frames (60 fps, camera and motion extrapolated),
    own-ship prediction 'present' and every feature that needs a fixed window. Adaptive delay (protocol 5) only when the
    session sets native_gate_lookahead = 'adaptive' (relay --adaptive): then lookahead_max defaults to 4 and pilot_delay,
    render_fps/camera/motion, wire crypto and peer links are skipped loudly ("protocol 5 ... excludes it").
  - Wire crypto (protocols 3/4): on when the session sets the credential native_gate_wire_crypto = "x4c1:..." (relay
    --wire-crypto); without one: DEFAULT_SKIPPED "the relay path is plain UDP with the shared token". Explicit crypto with
    adaptive, or crypto with peer links: refused before the boot (the relay refuses both combinations).
  - Peer links and NAT traversal: on only when the session sets native_gate_peer_window (and the rendezvous port) on every
    PC and the relay; otherwise DEFAULT_SKIPPED "not configured" (players would see each other's addresses).
  - Death vs on-foot bodies/slots (X4-Multiplayer-deathfoot is making them compatible): death, respawn 300 and the death
    suit are ON; pilot_foot_bodies and pilot_foot_slots are SKIPPED: "excluded by native_gate_pilot_death (on): ... death won
    by default". A session that sets bodies or slots explicitly wins over the default death (death skipped loudly). Both
    explicit: the probe's and the checker's rule refuse it. When deathfoot lands: drop the '!' tokens of these three entries.
  - UI guard and families: build, assets, faction need the guard, missions/conversation its groups, missiles pilot fire;

  - Every boot refusal of the probe (15 sites: fixed tick, wire 3, lookahead, adaptive, wire crypto, peer window, relay
    host, play mode, NPC rows, fast reads, tick rate, render frames/camera/motion/rows, start code): ERROR REFUSED <what>,
    info "the session could not start - refused <what> (<reason name>)". Before: a plain REFUSED row, the start menu idle.
  - Config refusals at load (every assert of the probe's top level): the probe body runs in pcall; ERROR CONFIG_REFUSED
    <why> + info line, then the error is raised as before.
  - Frame errors (asserts while arming or per tick): the existing ERROR row + ABORT, now with the info line "the session
    stopped - <why>".
  - Stops of the gate: the STOP row is followed by D.stop_notice: reason by name (D.STOP_REASONS, checked against the
    registry) and the piloting why: ERROR SESSION_STOPPED reason=N (<name>) why=...; reason 1 (the relay) gets an info line
    and a plain STOP_NOTICE row (the client cannot tell the relay's end from a mismatch the relay saw).
  - Every default that cannot apply: ERROR DEFAULT_SKIPPED key=... why=... feature=..., one combined info line.
  - Defaults refused (explicit combinations): ERROR DEFAULTS_REFUSED + info line + no boot. Module missing: DEFAULTS_MISSING.
  - Degraded counters in module statuses (D.watcher): a growing failures / *_failures / unmapped / *_unmapped / fallback /
    unknown / unsupported / refused / swap_refused / lost / torn counter, and the UI families' lua= skipped/dropped/refused
    parts: ERROR DEGRADED status=<row> <counter>=N (+delta) tick=T on every growth; an info line at most every 1800 ticks per
    counter (guard, missions and faction refusals already show their own info line: ERROR row only). Read from the 65
    statuses the frame polls, the UI *_STATUS rows, and 14 more statuses read every 600 ticks for this only (engine refresh,
    build RNG, portable math, exact reciprocal, fp env, decimal, macro arena, pick order, order canon, loadout order,
    lookahead, wire crypto, peer, UI guard). Before: counters only at the stride or the stop. The first live run will show
    which counters grow by design; those go to the module's own exception or a D.WATCH change.
  - HIT_CLAIMS_REFUSED (a claim refused on every client) and PILOT_NATIVE_REFUSED (a refused flight input): ERROR rows, the
    info line at most every 90 ticks. SHIP_ENROLL_REFUSED: ERROR + info. FORK_SAVE_SKIPPED: ERROR + info.
  - UI replay families' refusals: their info line is shown also without the guard (notify was nil without it).
  - The nav octree snapshot alone silently armed 'observe': ERROR DEGRADED nav_octree=observe.
  - The build script tools' empty loadout fallback (scripted runs): ERROR UI_BUILD_LOADOUT_EMPTY row.
  - The abort/stop path's status rows ran in pcall without a trace: a row that fails now writes ERROR STOP_ROW_FAILED <why>.
  - Info lines raised at the start menu (refusals before the snapshot load, which X4 does not draw there) are queued and
    shown again on the first frame with a game on screen; a ShowInfoLine that fails writes NOTICE_UNSHOWN.
